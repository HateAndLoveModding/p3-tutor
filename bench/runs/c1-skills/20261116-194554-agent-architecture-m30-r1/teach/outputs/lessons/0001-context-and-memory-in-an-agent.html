Context and memory in an agent

By the end of this lesson you can decide, for the makerspace assistant, what goes into the model's context at each step, what is saved between visits, and how it finds the right page in a long manual.

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits. Both depend on what the model sees on each call, and every token it sees costs money from a small budget. This lesson gives you the vocabulary and the decisions to defend at your design review.

          The context window: what the model sees 6 min

          Learning goals
          • Define a token and the context window.
          • List everything that occupies the window in one model call.
          • Explain why a fuller window costs more and can answer worse.
          What you need to know first
          • A language model takes text in and writes text out, from what a language model does.
          • The agent loop: ask, act, result, repeat, from the agent loop.

          The general idea

          A model reads and writes in pieces of text called tokens. A token is often a whole short word or a fragment of a longer one, so a page of text is several hundred tokens. You do not need to count them by hand; the API reports how many each request used.

          The context window is all the text the model can reference when it generates a response, including the response itself. It is separate from the training data: it works as the model's working memory for this one call (Claude API docs, Context windows). Whatever is not in the window, the model cannot use, no matter how much it learned in training.

          More than the student's question sits in the window. The system prompt, every message including tool results, and your tool definitions all count, and so does the output the model generates (Claude API docs). Tool definitions are easy to forget: a long, careful description of each tool is paid for on every call.

          Two limits follow. The first is hard: each model has a maximum window size, and an input that alone exceeds it is rejected with an error. Current Claude models have windows up to 1M tokens, so the hard limit is rarely your first problem. The second is soft, and it matters more to you. Cost grows with the tokens you send, and quality can fall as the window fills. Anthropic calls this context rot: as the number of tokens grows, the model's ability to recall information from the context decreases, so the goal is the smallest set of high-signal tokens that gets the job done (Effective context engineering for AI agents).

          Important steps

          • Inventory the window: system prompt, tool definitions, history, tool results, output.
          • Estimate the size of each part in tokens; the API's token counting tool can estimate a request before you send it.
          • Find the largest part and ask whether the model needs all of it for this step.
          • Remove or shorten what it does not need.

          Worked example: what one calendar question puts in the window

          The case

          A student asks, "Is the laser cutter free on Friday?" Your assistant has three tools: search_manuals, check_calendar and book_slot. The numbers below are invented to show the method; measure your own.

          Why this idea applies here: your sponsor's budget pays per token, so you need to know where the tokens go before you can cut any.

          1. Inventory. System prompt with makerspace rules: 600 tokens. Three tool definitions: 900. Student question: 15.
          2. Call 1. The model asks for check_calendar (about 40 tokens of output). Input so far is about 1,500 tokens.
          3. Tool result. The calendar tool returns the whole week's bookings for all 12 machines: 3,000 tokens, though the answer needs one line.
          4. Call 2. The input is now about 4,600 tokens. The largest part is the tool result, so that is where to cut.
          5. Fix. Change the tool to take a machine and a date and return only that machine's bookings: about 100 tokens. Call 2 input drops to about 1,700.

          The result: the same answer for about a third of the input tokens on call 2. The saving came from shaping a tool result, not from shortening the prompt.

          Common Mix-Ups

          "The context window is the model's memory of everything it knows"

          • Right: the window holds only the text of this call; training knowledge is separate.
          • Wrong: thinking facts from earlier chats or from your manuals are "in" the model.
          • Why: if the laser cutter manual's page is not in the window, the model answers from training patterns and can state a plausible, wrong setting with confidence, the failure you noticed in chatbots.

          "A bigger window means I can stop curating"

          • Right: what you put in matters as much as how much space exists.
          • Wrong: loading every manual because 1M tokens fit.
          • Why: you pay for every token each call, and recall degrades as the window fills.

            What is kept between steps 7 min

            Learning goals
            • Explain why each model call starts with no memory of the last one.
            • Trace how history grows across the steps of one request.
            • Choose between keeping, clearing and summarizing old content.
            What you need to know first
            • Tokens and the context window, from Section 1.
            • Your program runs each tool and makes a new model call with the result, from the agent loop.

            The general idea

            The model does not carry anything from one call to the next. What looks like memory inside a conversation is your program sending the earlier messages again. In the API, each turn's input contains all previous conversation history plus the new message, and previous turns are preserved completely (Claude API docs).

            This matters for the agent loop. Every step of the loop is a separate model call, and each call's input is the history so far: the question, each tool request the model made, and each tool result. The history only grows during a request. Step 5 therefore pays again for everything from steps 1 to 4, which is why a long, tool-heavy request can cost far more than its last step suggests.

            When history grows too large, there are three options, from lightest to heaviest:

            • Clearing: drop old tool results that the model no longer needs. Anthropic describes clearing old tool results as one of the lightest forms of trimming (Effective context engineering); the API offers it as tool result clearing under context editing.
            • Compaction: when a conversation nears the limit, summarize it and start a new window from the summary. The risk is that a summary can drop a detail you later need.
            • Isolation: a separate agent does messy work in its own window and returns only a short result. You will meet this in a later lesson on multiple agents.

            Important steps

            • Start each request with the system prompt, tools and the student's message.
            • After each tool call, append the model's request and the result to the history.
            • Resend the full history on the next call.
            • Before each call, check whether any block can be cleared or shortened.
            • If the history is still near the limit, summarize it and continue from the summary.

            Worked example: a booking request that touches three tools

            The case

            A student writes, "Book me the laser cutter Friday afternoon, and tell me the thickness limit for acrylic." The assistant must search the manual, check the calendar, then book.

            Why this idea applies here: the request needs four model calls, and you must know what each call carries to predict its cost and to decide what to clear.

            1. Call 1 carries the question. The model asks for search_manuals.
            2. Call 2 carries the question, that request and the manual passages (say 1,500 tokens). The model asks for check_calendar.
            3. Call 3 carries all of that plus the calendar result. The model asks for book_slot.
            4. Call 4 carries everything plus the booking confirmation. The model writes the final answer.
            5. Trim. The manual passages are needed to write the answer, so keep them. The calendar listing is not needed after the booking, so clear it before call 4.

            The result: the question is paid for four times, the manual passages three times. Clearing the calendar result saves it on call 4. The model never "remembered" anything; your program rebuilt the input each time.

            Common Mix-Ups

            "The model remembers the earlier steps"

            • Right: your program resends the history on every call.
            • Wrong: assuming the model holds earlier steps itself.
            • Why: if your code forgets to append a tool result, the next call has no trace of it, and the model may repeat the tool call or answer without the result.

            "Only the new step costs tokens"

            • Right: each call is billed on its whole input.
            • Wrong: costing a four-step request as four small calls.
            • Why: in the example above the question is paid for four times, so cost climbs faster than the step count.
            Check Yourself

            In a six-step request, step 3 returned a 5,000-token tool result the assistant never uses again. What happens to it if you change nothing?

              Retrieval: finding the right page 7 min

              Learning goals
              • Define retrieval and explain why it beats loading whole manuals.
              • Describe how a search tool turns a long manual into a few passages.
              • Judge what makes a retrieval result good enough to answer from.
              What you need to know first
              • Context rot and per-token cost, from Section 1.
              • Tools return results that enter the history, from Section 2.

              The general idea

              Retrieval means fetching only the pieces of stored information that a step needs and placing them in the context. The alternative is loading everything up front. Anthropic describes the pattern for agents as just-in-time: the agent keeps lightweight references, such as file paths, and loads data with tools when needed, instead of preloading all of it (Effective context engineering). The same article names the trade-off: exploring at run time is slower than having data ready, so many systems combine a little up-front context with retrieval for the rest.

              For a manual, retrieval has two halves. Before any question, you prepare the manual: split it into chunks of a few paragraphs, keeping the manual name and section heading with each. At question time, a search tool takes a query and returns the best few chunks. Ranking can use plain keyword matching, or it can use numeric representations of meaning so that "cut acrylic thickness" also finds "maximum sheet depth for PMMA". Which you use is an engineering choice to test on your own questions.

              The model controls the search. It writes the query, reads the result and can search again with different words if the first result missed. That makes retrieval a tool in the agent loop from the agent loop, with the same rules: it needs a clear description and a bounded result size.

              Two things go wrong. A search can return the wrong chunk, and then the model answers from something close but incorrect. Or it can return nothing useful, and the model, if not told to admit it, fills the gap from training patterns. Your system prompt should say: answer from the returned passages, cite the manual and section, and say so when the passages do not contain the answer.

              Important steps

              • Split each manual into chunks that keep a title, section and page.
              • Give the model a search tool that returns a small, fixed number of chunks.
              • Let the model rewrite the query and retry when results look wrong.
              • Require the answer to cite the chunk it came from.
              • Tell the model to say "not found" when the passages do not answer.

              Worked example: the acrylic thickness question

              The case

              The makerspace has a 120-page laser cutter manual. Assume about 60,000 tokens (an invented size for illustration). A student asks, "How thick can acrylic be on the laser cutter?"

              Why this idea applies here: sending 60,000 tokens on each of four calls would be about 240,000 input tokens for one answer, and recall would suffer. The answer sits in perhaps one page.

              1. Prepare. Before launch, split the manual into about 300-token chunks, each labelled "Laser Cutter Manual, section 4.2, page 37".
              2. Query. The model calls search_manuals with "laser cutter acrylic maximum thickness".
              3. Return. The tool returns the top three chunks, about 900 tokens, with their labels.
              4. Check. Chunk 1 is the materials table with an acrylic limit. Chunk 3 is about the older machine in the shop's storage room. The model must pick chunk 1 by its label.
              5. Answer. The model states the limit and cites "section 4.2, page 37", so the student can verify it.

              The result: about 900 tokens of manual instead of 60,000, and an answer the student can check. The labels did two jobs: they let the model discard the wrong chunk and they let the student verify.

              Common Mix-Ups

              "Retrieval means the model knows the manual now"

              • Right: retrieved chunks are in the window for these calls only.
              • Wrong: treating retrieval as teaching the model.
              • Why: on a later question the model has no chunk unless it searches again, so a missing search gives an answer from training.

              "A summary of the manual is as good as the manual"

              • Right: keep the original text and retrieve from it.
              • Wrong: replacing the manual with a short summary to save tokens.
              • Why: a summary drops exact limits and steps, and a laser setting that is "about right" is a safety problem.

                Notes: memory between sessions 7 min

                Learning goals
                • Separate short-term context from long-term stored memory.
                • Explain how a memory tool lets the model save and read notes.
                • Decide what the assistant should store about a student, and what not.
                What you need to know first
                • History is resent on every call and lost when you stop sending it, from Section 2.
                • Retrieval puts stored text into the window on demand, from Section 3.

                The general idea

                A session is one conversation: one run of the loop with one history. When it ends, the history is gone unless your program stored it. A student who returns on Thursday starts a new session with an empty window. Memory in an agent means information saved outside the window, so a later session can load it.

                The pattern is the same as retrieval, with one addition: the agent also writes. Anthropic calls this structured note-taking: the agent regularly writes notes to storage outside the context window and pulls them back later (Effective context engineering). The Claude memory tool is one version. It lets the model create, read, update and delete files in a /memories directory that persist between sessions (Memory tool docs).

                The memory tool runs on your side. The model only requests a file operation; your application carries it out, against storage you choose, such as a database, and returns the result. Your program, not the model, decides where the data lives, how long it is kept and what paths are allowed. The docs require handlers to reject paths outside /memories (Memory tool docs).

                Notes are not a place to dump everything. Each note read back occupies the window, with the same cost and rot as anything else. Store short, durable facts that a future session would otherwise have to ask for again. Do not store sensitive personal data you do not need. The docs say Claude usually refuses to write sensitive information to memory files, but recommend validation in your handler for stronger guarantees.

                Important steps

                • Decide what a future session needs: facts that last and that change decisions.
                • Keep per-student notes small and separate, one record per student.
                • At session start, load that student's record into the context.
                • During the session, update the record when something durable changes.
                • Validate paths and content in your handler, cap file sizes and expire old records.

                Worked example: remembering training status

                The case

                On Monday, a student completes the laser cutter safety training. On Thursday they ask to book the laser cutter. The rule: only trained students may book it.

                Why this idea applies here: Thursday's session has an empty window, and the booking rule is a safety rule. Asking the student whether they are trained is unreliable; the saved record is the source of truth.

                1. Save. Monday, the training system confirms completion. The assistant (or your code) writes /memories/students/s1042.md: "Trained: laser cutter, 2026-11-16. Prefers afternoon slots."
                2. Load. Thursday, a new session begins. Your program identifies the student and the model views that file first, about 40 tokens.
                3. Decide. The model sees "Trained: laser cutter" and proceeds to the calendar and booking tools. For a CNC router request, the record has no entry, so it says training is needed.
                4. Update. After the booking, a note is added only if something durable changed, such as a new preference.

                The result: 40 tokens of memory replace an unreliable question, and the model sees nothing about other students. A safer design stores the training flag in your own database and has code check it; notes suit softer facts like preferences. Choosing which is a design-review decision.

                Common Mix-Ups

                "The model learns from each student's chat"

                • Right: the model's knowledge does not change when you talk to it; saved notes are text you reload.
                • Wrong: expecting the assistant to remember a student with no stored record.
                • Why: without a saved note, Thursday's session has no trace of Monday, so the assistant would treat the student as new.

                "More memory is better memory"

                • Right: store little and load only what the step needs.
                • Wrong: saving full transcripts and loading all of them at every session start.
                • Why: transcripts bring the cost and rot problems back, and they keep personal data longer than needed.

                  Main points 1 min

                  • The context window is everything the model can use in one call: prompt, tool definitions, messages, tool results and the output.
                  • More tokens cost more and can reduce recall, so aim for the smallest set of useful tokens.
                  • The model keeps nothing between calls; your program resends the history, so early content is paid for again at every later step.
                  • Trim by clearing old tool results, shaping tool outputs, or summarizing near the limit.
                  • Retrieval fetches a few labelled chunks of a manual on demand instead of loading it all.
                  • Memory is stored outside the window, written and read by your program, and survives between sessions.
                  • Store short durable facts, load only what a step needs, and keep safety-critical checks in code.
