1. The context window 6 min

Learning goals
  • Say what the context window is and what counts toward it.
  • Explain why a bigger context costs more and can answer worse.

The general idea

The context window is all the text a model can reference when it writes a response, including the response itself. It is not the training data; it is what the model is given for this one call (Claude docs: Context windows). Text is counted in tokens, small pieces of words, and the window has a maximum size in tokens.

Everything in the request counts toward the window:

  • the system prompt (the assistant's role and rules);
  • your tool definitions, even for tools the model never calls;
  • every message so far, including tool results;
  • the response the model writes in this call.

Two consequences matter for your budget and your design:

  • Cost. Input tokens are billed; the earlier history is sent again as input on each call (docs). A long context costs more on every call it is part of.
  • Quality. As the number of tokens grows, the model's accuracy and recall degrade. This is called context rot. Anthropic describes context as a finite "attention budget" and recommends the smallest set of high-signal tokens that makes the right outcome likely (Effective context engineering for AI agents).

You need from earlier: the agent loop, and that a model reads text and writes text a token at a time (record 0001).

Worked example: counting one request

Worked example (round numbers invented for illustration)

A student asks: "Is the laser cutter free Friday at 3 pm, and do I need training?" The model calls check_calendar, then search_manuals, then check_training_record, then answers: four model calls. Here is what each call receives as input.

  1. Call 1: system prompt 800 + three tool definitions 600 + question 30 = 1,430 tokens.
  2. Call 2: call 1's input, plus the model's tool request (50) and the calendar result (150) = 1,630.
  3. Call 3: call 2's input, plus a request (50) and three manual pages returned by search_manuals (3,000) = 4,680.
  4. Call 4: call 3's input, plus a request (50) and the training record (100) = 4,830, and the model now writes the answer.
  5. Total billed as input: 1,430 + 1,630 + 4,680 + 4,830 = 12,570 tokens, although the final context is only 4,830.

Why this matters: the 3,000-token manual result is paid for twice, in calls 3 and 4. Large tool results are the biggest lever on cost per request.

A common mix-up

Wrong: "A bigger context window means I can put the whole manual in and get better answers." Right: the window is a limit on what fits, not a promise that everything in it is used well. Recall degrades as it fills, and each token is billed on every call it appears in. Tempting because a larger window sounds like more intelligence; it is only more room.

Check yourself

In the worked example, the team removes the calendar tool but leaves its definition in the request. What is true?

Third option: tool definitions are part of every request, so they count toward the window and are billed on each call, used or not.

2. What is kept between steps 6 min

Learning goals
  • Explain how the agent "remembers" earlier steps within one request.
  • Name two ways to shrink context as a run grows: clearing tool results and compaction.

The general idea

Within a run, the model keeps nothing by itself. Each call starts fresh from the text it is sent. The program keeps the conversation as a list of messages and, on every step, sends the whole list again: previous turns are preserved completely and accumulate until the window nears its limit (Claude docs). That list is the agent's short-term memory.

Steps to manage it:

  1. Append each model output and each tool result to the list.
  2. Send the list with the next call.
  3. When it grows too large, shrink it deliberately, before it hurts quality or cost.

Two shrinking tools, from lightest to heaviest (Anthropic):

  • Tool result clearing: remove raw tool outputs deep in the history, such as an old 3,000-token manual search, once the model has used them.
  • Compaction: summarize a conversation nearing the limit and continue in a new window with the summary. Keep decisions and unresolved problems; drop redundant tool output.

You need from earlier: the loop (record 0002) and the token counting from section 1.

Worked example: clearing the manual result

Worked example

Same request as section 1. After call 3 the model has already noted "laser cutter requires the safety course" from the manual pages, so the pages are no longer needed.

  1. The program replaces the 3,000-token manual result with a one-line placeholder such as "[manual search result cleared]" (about 10 tokens).
  2. Call 4's input falls from 4,830 to about 1,840.
  3. The model's own tool request and its note remain, so it still knows what it found. The cost: if it later needs the exact wording, it must search again.

Why: the answer needs the conclusion from the pages, not the pages. Clear what is spent; keep what is decided.

A common mix-up

Wrong: "The model remembers the previous steps itself." Right: the program re-sends them. If the program forgets to include a step, the model has no trace of it. Tempting because a chat feels continuous; the continuity is the message list.

Check yourself

A booking run is at 90% of the window, and the first half is only failed date lookups the model has already learned from. Which action fits best?

Show the answer

Third option. Old, spent tool results are the safest content to remove; the conclusions are what the next step needs.

3. What is kept between sessions: notes 6 min

Learning goals
  • Explain why nothing carries over between sessions unless your program saves it.
  • Describe notes as memory: written to storage outside the context, read back later.
  • Decide what the assistant should write down.

The general idea

When a session ends, its message list is gone, and a new session starts with whatever the program puts in the request. Nothing is automatic. For the assistant to know on Tuesday that a student finished laser training on Monday, something must write that down and something must read it back.

This is structured note-taking, or agentic memory: the agent writes notes to storage outside the context window and reads them back at later steps or sessions. Anthropic's examples are a to-do list and a NOTES.md file, and a game agent that resumed after context resets by reading its own notes (Anthropic).

One concrete form is the memory tool: Claude can create, read, update and delete files under a /memories directory that persist between sessions. It runs client-side: the model requests a file operation, and your application performs it against storage you control and returns the result as a tool result (Memory tool docs). You can build the same thing yourself with a Python dict saved to a JSON file and two tools, read_note and write_note.

  • Write down: facts that must outlive the session and are cheap to store: training completed, dates, a student's stated needs, a half-finished booking.
  • Do not write down: raw tool output, whole manual pages, or anything the program can look up fresh (the calendar changes; read it live).

You need from earlier: tools are run by the program (record 0002); section 2's message list.

Worked example: Sam's training status

Worked example

Monday: Sam, a student, finishes the laser cutter safety course with the assistant's help. Tuesday: Sam returns and asks to book the cutter.

  1. Monday, at the end: the model calls write_note with {"student": "sam", "laser_training": "complete", "date": "Mon"}. The program saves it. Why: this fact is small and needed later.
  2. Tuesday, call 1: the program starts with an empty message list. The system prompt tells the model to read the student's note first, so the model calls read_note("sam").
  3. The result, about 30 tokens, enters the context. The model books the slot without asking Sam to retake training.
  4. Cost: 30 tokens per session instead of replaying Monday's whole conversation, which could be thousands.

Because notes can be wrong or stale, store the date, and send a booking through the real calendar tool rather than trusting a note about availability.

A common mix-up

Wrong: "A good agent automatically remembers earlier conversations." Right: memory exists only if you build it: something writes, something reads, and you decide what is kept. Tempting because chat apps seem to remember; they have extra machinery behind them. Also, a note stored about a student is personal data, so store only what the assistant needs.

Check yourself

4. Retrieval: finding the right page 7 min

Learning goals
  • Explain why a long manual is retrieved from, not loaded whole.
  • Contrast up-front retrieval with just-in-time retrieval, and choose for the makerspace.

The general idea

Retrieval means fetching only the pieces of a large source that the current question needs and placing them in the context. Manuals are far too long to load whole, by section 1's cost and recall arguments. Anthropic describes two patterns (Anthropic):

  • Up front (pre-inference): before the model runs, the program searches the manuals, for example by embedding-based search, which finds text by meaning, and adds the best passages to the prompt. Fast, one step. The risk: the program decides what is relevant before the model has reasoned.
  • Just in time: the agent keeps lightweight identifiers (file names, page numbers, stored queries) and uses a tool such as search_manuals or read_page to load what it needs, when it needs it. More flexible, slower, and it needs good tool descriptions so the model does not waste context.
  • Hybrid: load a small amount up front, such as a short index of the manuals, and let the agent explore the rest.

Retrieval is different from notes: retrieval reads a source that already exists and is the same for everyone (manuals); notes record what this agent learned about this student or task.

You need from earlier: tools and descriptions (quiz 0001), and sections 1 and 2.

Worked example: "How do I change the lens on the laser cutter?"

Worked example

The laser cutter manual is 120 pages. Loading it whole would be tens of thousands of tokens on every call, and the answer is on two pages.

  1. Prepare once (not per question): split the manual into sections, each with a title and page number.
  2. Hybrid start: keep a short table of contents (about 300 tokens) in the system prompt, so the model knows what sections exist.
  3. Search: the model calls search_manuals("laser cutter lens replacement"). The program returns the top three sections as titles with short excerpts, not full pages.
  4. Read: the model picks one and calls read_section("laser-cutter", "7.3"), receiving about 800 tokens.
  5. Answer and cite the section number so the student can check it.

Why this design: two small results (about 1,000 tokens) replace a 120-page load, and a section number gives students something to verify against.

A common mix-up

Wrong: "Retrieval means the model finds the page itself from what it remembers of the manual." Right: the model only sees what is placed in its context; a search tool, run by the program, finds the text. If the search returns the wrong page, the model answers from the wrong page, so retrieval quality caps answer quality.

Check yourself

The team's manuals change each semester and the machines have different manuals. Which retrieval design fits best?

Show the answer

Second option: a small index plus search and read tools, so only the needed sections enter the context and updated manuals are picked up automatically.

Summary 2 min

  • The context window is everything the model sees in one call; every token is billed on every call it is in, and a fuller context can recall worse.
  • Between steps, the program re-sends the message list; shrink it with tool result clearing or compaction.
  • Between sessions, nothing carries over except what your program saves as notes and reads back.
  • Long manuals are retrieved from, up front, just in time, or both, not loaded whole.

Say it in your own words: without looking, explain to a teammate what is in the context at call 3 of a request, and what would be lost if the program were restarted before the next session.
