Context and memory in an agent

By the end of this lesson you can decide, for any fact the makerspace assistant needs, whether it belongs in this turn's context, should be fetched by retrieval, or has to be saved as a note for next session.

Why this matters for you

This is success criterion three in your mission: deciding what your makerspace assistant keeps in context, what it saves between visits, and how it finds the right page in a long machine manual.           1. The context window 7 min

          Learning goals
          • Define the context window and list what counts toward it.
          • Explain why a bigger context window does not automatically mean better or cheaper answers.
          • Decide whether a piece of information belongs in context right now, or should be kept out of it.
          What you need to know first
          • The agent loop: the model is given a goal and tools, asks for an action, the program runs it, the result comes back, and this repeats until the model gives a final answer or a limit is reached (quiz 0001).
          • A language model only knows what it learned in training plus what is in the text it is given right now; it has no memory of its own between separate calls (learning record 0001).

          The general idea

          Every time the model is called, it is handed one single bundle of text to read before it writes anything back. That bundle is the context window: the complete set of text available to the model for this one call, including the response it is about to generate. It is not the large pile of data the model was trained on; training is fixed long before you ever call it. The context window is closer to a working memory for this one call only (Claude Docs, "Context windows").

          Models read and write in tokens, small chunks of text usually shorter than a whole word. Everything in a request counts toward the context window and gets billed as tokens: the system prompt, every prior message, every tool result, and the descriptions of the tools the model is allowed to use, plus whatever the model generates in reply (Claude Docs, "Context windows"). Each model has a fixed ceiling on this total, commonly 200,000 or up to 1,000,000 tokens depending on the model. Go over that ceiling on a single call and the call fails outright.

          Tokens are also the unit cost is measured in: a call that resends a long tool result pays for every one of those tokens again, even if the model never ends up using most of them. This is why a long machine manual, loaded into context in full on every question, is not just risky for the window's ceiling; it is expensive on every single call that carries it.

          A second, separate problem shows up well before the ceiling: context rot, where the model's ability to accurately recall and use information drops as the number of tokens in context grows, even when there is still room left (Anthropic, "Effective context engineering for AI agents"). A bigger context window buys more room; it does not buy better use of that room. The two problems point the same way: put in context only what this call actually needs, and keep the rest out until it is needed.

          Important steps

          • Before trusting a call's output, know what is actually inside its context window: system prompt, full message history so far, tool definitions, and every tool result still in the transcript.
          • Know the ceiling for the model you are using, and remember it is a hard limit, not a soft guideline.
          • Treat token count as a cost, not just a size: more tokens in context means more billed on every call that carries them forward.
          • Watch for context rot: do not assume more context is safe just because it fits; curate what is actually relevant to this call.

          Worked example: a booking question that touches three tools

          The case

          A student messages your makerspace assistant: "Can I use the laser cutter Friday afternoon, and do I need training?" The assistant has three tools: search_manuals, check_training_record, and check_calendar.

          Why this idea applies here: before the third tool call, the context window already holds everything built up so far, and how big that first tool result is decides how expensive and how reliable every call after it will be.

          1. Call 1's context: system prompt, the three tool descriptions, and the student's question. Nothing else yet, so this call is small.
          2. Suppose search_manuals is poorly designed and returns the laser cutter's entire 120-page manual as its result. That result alone could run into the tens of thousands of tokens, and it is now part of the transcript going forward.
          3. Call 2's context: everything from call 1, plus that whole manual, plus the model's request for check_training_record. The manual dump is resent and rebilled on this call even though only one paragraph of it answers the question.
          4. By call 3 (check_calendar) and call 4 (the final answer), the same oversized manual is still sitted in context, still being resent, still raising the chance of context rot on everything else in that call.

          The result: a tool that returns too much turns one question into an expensive, rot-prone task. A better-designed search_manuals would return just the relevant paragraph on training requirements, a few hundred tokens instead of tens of thousands — the fix this lesson builds toward in Section 4.

          Common Mix-Ups

          "A bigger context window means better answers"

          • Right: a bigger window gives the model more room to work with, nothing more.
          • Wrong: assuming a model with a 1,000,000-token window will answer more accurately than one with a 200,000-token window just because it can hold more.
          • Why: recall degrades as tokens accumulate, window size or not — this is context rot. A huge window that gets filled with an entire manual can perform worse on the one paragraph that matters than a small window holding only that paragraph.

          "The context window is just the current message"

          • Right: the context window is everything sent in that one request: system prompt, the full message history, tool definitions, and every tool result still in the transcript.
          • Wrong: thinking only the newest user message or the newest tool result counts.
          • Why: this is exactly what you cannot see unless you count it — and it is also exactly what you are billed for on every call, which is why tokens matter for cost.

            2. What's kept between steps 6 min

            Learning goals
            • Trace what carries forward from one step of the agent loop to the next, within a single task.
            • Explain why "the agent remembers the last step" really means "the program resent everything, including the last step."
            • Decide what to do when a growing transcript threatens to approach the context window's ceiling mid-task.
            What you need to know first
            • The agent loop repeats: action requested, action run, result returned, repeat (quiz 0001).
            • Section 1: the context window is everything sent on one call, and bigger is not automatically better.

            The general idea

            Within one run of the agent loop — one task, from the student's first question to the assistant's final answer — the context window does not reset between steps. Each time the loop calls the model again, the program sends the entire conversation so far, not just whatever is newest. Previous turns are preserved completely, and the window grows with every one of them (Claude Docs, "Context windows").

            This is the real mechanism behind something that looks like memory. If the model correctly uses, on step 7, a fact that a tool returned back on step 2, it is not because the model stored that fact anywhere. The model has no state between calls; each call only has what is in its input, which is the same floor you already know from language models in general. What actually happened is that the program resent step 2's result as part of step 7's input, bundled with everything in between. The "remembering" is entirely the program's doing, not the model's.

            That matters in two ways. First, nothing is ever truly private to one step; a tool result from early in a task is still fully present, in full, many steps later, unless something actively removes it. Second, because the transcript only grows, a long enough task can approach the context window's ceiling before it is done, especially if any single tool result is large. At that point the choices are to summarize older turns down to what still matters, to clear a stale tool result that is no longer needed, or to stop the loop and hand the problem back — the same stopping-condition idea from quiz 0001's step-limit question, applied to the window filling up rather than to the loop repeating itself.

            Important steps

            • Every model call in the loop resends the system prompt plus the full transcript so far — never only a diff of what changed.
            • Each tool result is appended to that transcript and stays there, fully, until the task ends or something actively drops it.
            • Track the running total of tokens against the context window's ceiling as the task runs, not only at the start.
            • When the total is getting close to the ceiling: summarize older turns, clear tool results no longer needed, or stop the loop — do not just hope the next call fits.

            Worked example: one booking request, four calls

            The case

            Back to the laser cutter question from Section 1, now tracing exactly what each of the four model calls sees, assuming search_manuals and check_training_record are both well-behaved and return short, relevant results.

            Why this idea applies here: seeing the input to each call laid out shows precisely what "carries forward" means, and why a large result at any one step inflates every call after it, not just that one.

            1. Call 1 input: system prompt, tool descriptions, the student's question. Call 1 output: a request to run search_manuals("laser cutter", "training requirements").
            2. Call 2 input: everything from call 1, plus search_manuals's result (the one relevant paragraph). Call 2 output: a request to run check_training_record(student_id, "laser cutter").
            3. Call 3 input: everything from calls 1 and 2, plus check_training_record's result. Call 3 output: a request to run check_calendar("laser cutter", "Friday").
            4. Call 4 input: everything from calls 1 through 3, plus check_calendar's result. Call 4 output: the final answer to the student, built from facts gathered three steps and two steps ago, still sitting in context.

            The result: the final answer can correctly combine the manual's training rule, the student's record, and Friday's calendar only because all three results are still physically present in call 4's input. None of it was "remembered" by the model between calls; all of it was resent.

            Common Mix-Ups

            "The model remembers what happened two steps ago"

            • Right: it looks remembered because the program resends it, call after call.
            • Wrong: believing the model is holding on to that fact itself, independent of what the program sends it.
            • Why: the distinction matters in practice — if the program ever stops resending something, it is genuinely gone from the model's reach; there is no model-side backup to fall back on.

            "It fits now, so I don't need to think about it"

            • Right: watch the running total across the whole task, not just this call's snapshot.
            • Wrong: checking only whether the current call fits and assuming later calls will too.
            • Why: the transcript only grows. A task that repeats many times with no stopping condition, like quiz 0001's 40-step bug-fixing loop, keeps every one of those 40 steps in context, and a window that was comfortable at step 5 may not be at step 35.

              3. What's kept between sessions 7 min

              Learning goals
              • Tell what carries forward within one run of the loop from what persists after that run ends.
              • Explain why nothing crosses between separate sessions by default.
              • Decide what the makerspace assistant must save explicitly, and where, to know a returning student.
              What you need to know first
              • Section 2: within one task, context grows because the program resends the transcript on every call.
              • A model only knows what it learned in training plus what is in its current input (learning record 0001).

              The general idea

              A session ends: the task is done, the student closes the chat, the booking is confirmed. Unless the program explicitly wrote something to storage outside that conversation, the next session begins with a fresh context window containing only whatever the program puts into it this time — a new system prompt, the new question, and nothing about what happened before. The model has no built-in way to reach back into a conversation that already ended; that is the same floor as a single call, just applied across the gap between sessions rather than within one task.

              This is the real line between "agent" and "agent that remembers you": persistence — information surviving past the end of the session that produced it — has to be built, not assumed. What persists is whatever gets written to storage that lives outside any one conversation, such as a file or a row in a database, and then deliberately loaded back into context at the start of a later session (Anthropic, "The components of agent memory"). For your assistant, a student's completed-training status has to live in a database your booking tool reads, because last Tuesday's chat is simply not there anymore to ask.

              There is a cost trap to avoid here too: you could try to persist everything by reloading an entire past conversation at the start of every new session, but that reintroduces Section 1's problem — more tokens, more cost, more context rot, most of it irrelevant to today's question. The craft is deciding what small, specific fact is worth carrying forward, not reloading everything just in case.

              Important steps

              • Ask of any fact: does it disappear when this session ends? By default, yes, unless the program saves it elsewhere.
              • Decide what must survive regardless of how the next session starts, such as "completed laser cutter training on this date."
              • Write that fact somewhere outside the context window: a database row, a file — not "trust the model to remember."
              • At the next session, load back only the specific fact needed, not the whole prior conversation.

              Worked example: a student returns three days later

              The case

              On Monday, a student completes laser cutter safety training. The assistant walks them through a checklist, and a staff member confirms completion in the chat. On Thursday, the same student messages the assistant asking to book the laser cutter.

              Why this idea applies here: Thursday's message starts a session with an empty context window; whether the assistant can correctly say "yes, you're cleared" depends entirely on whether Monday's session wrote that fact down anywhere Thursday's session can read.

              1. Monday's session, at the moment training is confirmed, calls a save_training_record(student_id, "laser cutter", date) tool that writes one row to a database. This is the only thing that survives Monday's session ending.
              2. Monday's conversation then closes. Its transcript, if kept at all, sits in a log somewhere, but nothing automatically feeds it into any future session.
              3. Thursday's session starts fresh: system prompt, tool descriptions, the new question. No trace of Monday's chat is in there.
              4. When the assistant needs to know whether the student is trained, it calls check_training_record(student_id, "laser cutter"), which reads Monday's saved row — a few dozen tokens, not Monday's transcript.

              The result: Thursday's assistant correctly says "yes, you're cleared for Friday," not because it remembers Monday, but because Monday's session took the one deliberate step of saving a fact that Thursday's session took the one deliberate step of reloading.

              Common Mix-Ups

              "A long enough conversation would make it remember me next time"

              • Right: once a session ends, the next session starts with a context window the program fills fresh.
              • Wrong: thinking that how long or detailed a past conversation was affects whether anything carries over.
              • Why: length never matters here, only whether something was explicitly saved. A ten-minute chat that ends with a saved record beats a two-hour chat that ends with nothing written down.

              "A bigger context window would let it remember past sessions"

              • Right: window size only governs how much one call can hold; it has nothing to do with whether an earlier, separate session is reachable.
              • Wrong: assuming a model with a 1,000,000-token window naturally "remembers more" across visits than one with a smaller window.
              • Why: even a huge window starts a new session empty unless the program loads something into it; this is Section 1's ceiling applied to the wrong problem.

                4. Retrieval and notes as memory 7 min

                Learning goals
                • Tell retrieval from notes as two different ways to make an agent act like it has memory.
                • Decide which one fits "finding the right page in a long manual" versus "remembering a fact about one student."
                • Explain why both exist to keep what lands in context small, not just to make facts available somewhere.
                What you need to know first
                • Section 3: persistence requires something saved outside the session and reloaded later.
                • Section 1: context rot and cost both push toward keeping only what is relevant in context.

                The general idea

                Once you accept that nothing persists for free, two patterns cover most of what an agent needs to look like it remembers.

                Retrieval keeps a large body of source material, such as the machine manuals, entirely outside the context window. The material is split into smaller pieces, often called chunks, and on each question the program searches for just the chunks relevant to that question, feeding only those into context as a tool result, instead of the whole document (Anthropic, "Contextual retrieval in AI systems"). Retrieval answers "where do I find the right information inside something too big, or too wasteful, to resend in full on every call."

                Notes are the other pattern: the program, or the model through a tool, writes a short, structured summary of one specific fact worth keeping, stores it outside the conversation, and loads that short note back into context next time, instead of the raw transcript it came from (Anthropic, "Effective context engineering for AI agents"). Notes answer "what is the compact fact worth carrying forward, now that the conversation that produced it is gone." Section 3's saved training record was exactly this: one row, not a transcript.

                The two combine naturally. Your assistant retrieves from the manuals to answer "how do I turn on the exhaust fan," and reads or writes a note to answer "is this particular student allowed to." Neither pattern is "give the model everything, just in case" — both exist specifically to avoid that, which is the same discipline from Section 1 applied on purpose.

                Important steps

                • For a large, mostly fixed reference like a manual: split it into chunks ahead of time; search and pull in only the matching chunk or chunks per question.
                • For a small, per-student fact like training status: write a short note when the fact is established; store it keyed to that student; load it back by that key next session.
                • Keep whatever lands in context small and specific either way — a search that returns ten chunks "just in case" or a note that has grown into a full history re-creates Section 1's cost and rot problem.
                • Decide between the two by asking: is the source big and mostly unchanging (retrieval), or small and shaped by what just happened in this conversation (a note)?

                Worked example: one question, two memory needs

                The case

                A student asks: "How do I turn on the laser cutter's exhaust fan, and am I cleared to use it?" This single question needs two different kinds of information the assistant does not already have in context.

                Why this idea applies here: one half of the question needs a fact buried in a long, fixed document; the other half needs a small fact about this one student that was set once and should be carried forward. Treating both the same way, by stuffing everything into context, would waste most of the window on material that answers neither half well.

                1. For the exhaust fan instructions: search_manuals searches the laser cutter manual's chunks for "exhaust fan," and returns only the page covering the switch sequence — a few hundred tokens, not all 120 pages. This is retrieval.
                2. For whether the student is cleared: check_training_record reads back the note written in Section 3's worked example — one saved row, not the Monday transcript that produced it. This is a note.
                3. Both small results land in the current call's context alongside the question. Nothing else — not the rest of the manual, not any other student's record — ever enters context at all.

                The result: the assistant answers both halves of the question accurately, using a combined context that is a small fraction of what "load everything, to be safe" would have required, and at a small fraction of the cost.

                Common Mix-Ups

                "Retrieval means giving the model the whole document"

                • Right: retrieval searches first and sends only the matching chunk or chunks.
                • Wrong: thinking retrieval is just another word for loading an entire document into context so the model "has everything."
                • Why: the whole point of retrieval is to avoid sending the whole document; sending it all defeats the purpose and brings back Section 1's cost and context-rot problems on every call.

                "A note is just a saved copy of the conversation"

                • Right: a note is a deliberately compact, structured summary of one specific fact, such as one database row.
                • Wrong: treating "writing a note" as the same thing as "keeping the full conversation around for later."
                • Why: notes are small on purpose, so loading them back stays cheap and accurate; saving whole transcripts as "memory" just moves the context-rot and cost problem to a later session instead of solving it (Anthropic, "The components of agent memory").

                  Main points 1 min

                  • The context window is everything sent to the model on one call: system prompt, full message history, tool definitions, and every tool result still in the transcript, up to a fixed token ceiling.
                  • More tokens in context is not free and not automatically better: cost rises with every token resent, and recall degrades as context grows (context rot), so curate what is in context rather than maximizing it.
                  • Within one run of the agent loop, the model holds no state of its own between calls; the program resends the growing transcript every call, which is what makes an earlier step look remembered.
                  • A session's context window disappears when the session ends. Nothing carries to the next session unless the program explicitly saves it outside the conversation and reloads it.
                  • Retrieval keeps a large, mostly fixed reference outside context and searches it, pulling in only the matching piece per question.
                  • Notes are short, structured summaries of specific facts, written outside the conversation and reloaded by key at the start of a later session.
                  • Choose retrieval for big, mostly static material; choose a note for a small per-student fact that is set once and should carry forward.
