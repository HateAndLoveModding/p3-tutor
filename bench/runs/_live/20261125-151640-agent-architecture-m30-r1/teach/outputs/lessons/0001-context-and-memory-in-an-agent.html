Context and memory in an agent

By the end of this lesson you can decide, for any piece of information your assistant touches, whether it is already sitting in context, needs to be fetched by retrieval, or has to be written down as a note so a later session can read it back.

Objective O3: the context window, what's kept between steps and between sessions, and retrieval and notes as memory About 30 minutes Builds on the agent loop
Why this matters for you

Your makerspace assistant has to answer from long machine manuals without blowing the sponsor's small model budget, and it has to remember a student's training status days after the conversation that established it has ended. Both are this lesson's two problems: what stays in context on one call, and what you make stay around for the next one.

        Section 1: The context window 9 min

        Learning goals
        • Define the context window in terms of tokens, and name what counts toward it on every call.
        • Explain why a bigger context window does not automatically remove the budget or the accuracy problem.
        • Decide, for a piece of text, whether sending it this turn is worth its share of the budget.
        What you need to know first
        • A language model turns text into more text, one token at a time, from patterns learned in training, from this workspace's first learning record.
        • The agent loop calls the model repeatedly, and each call is a separate request that is given the result of the last action, from the agent loop record.
        • Token: the small chunk of text, often close to a word or word-piece, that a model reads or writes one at a time. It came up in passing before; this is its first real definition.

        The general idea

        The context window is "all the text a language model can reference when generating a response, including the response itself"; it is a "working memory" for one call, not the much larger corpus the model was trained on (Claude Platform Docs, Context windows). Everything in a request counts toward it: the system prompt, every message including tool results, images and documents, the tool definitions themselves, and the output the model generates for that call.

        Because the agent loop resends the whole running history on every call, the context window grows every step, and the model's provider bills for all of it: input tokens are counted on every single call, not once when they were first produced. A long tool result that gets carried forward costs money again on call 6, call 7 and call 8, not just on the call that fetched it. This is the direct lever on a small, sponsor-set model budget.

        A bigger window does not remove this. Accuracy and recall degrade as token count grows, a pattern Anthropic calls context rot (Claude Platform Docs): the model has to weigh far more possible relationships between tokens as the count rises, so a model that technically fits an entire manual in its window can still answer worse once it is carrying everything it might ever need, compared with being given only what this question needs.

        Important steps

        • Before sending something into context, ask whether it has to be resent on every later call too — once it's in, it stays in until something removes it.
        • Track what counts: the system prompt and instructions, every tool's schema, every past message and tool result, and this call's own output.
        • Prefer a small, relevant slice of a source over the whole thing "to be safe"; a bigger window raises the ceiling, it doesn't lower the cost or protect accuracy.

        Worked example: a laser-cutter question grows the window

        The case

        A student messages your makerspace assistant: "Can I use the laser cutter? I think I need training." The harness sends the model a system prompt (about 300 tokens of role and rules), three tool schemas — check_calendar, search_manuals, check_training_record (about 200 tokens combined) — and the student's message (about 20 tokens). That is roughly 520 tokens before any answer work begins.

        Why this idea applies here: the design review has to defend the assistant against a small, sponsor-set budget, and this question is about to call two more tools, each of which adds tokens that get resent on every later call in this same session — exactly the compounding cost the general idea describes.

        1. The model calls check_training_record; the program runs it and returns "not certified" (about 15 tokens), which joins the growing message list and will be resent on every call after this one.
        2. The model calls search_manuals("laser cutter safety training"). If this tool is written to return the entire safety chapter, that is roughly 2,400 tokens landing in context in one shot — about 4 to 5 times everything sent so far, combined.
        3. That 2,400-token chapter now sits in context for the rest of the session: every later call this conversation makes resends it, and the model must weigh it against the roughly 40 tokens that actually answer "do I need training," which is exactly the context-rot risk the general idea raised.

        The result: the assistant still answers correctly this turn, but at a token cost, repeated on every later call, that a full-chapter tool makes worse than it needs to be. That gap — pulling in only the relevant piece of a large source — is what Section 3's retrieval approach is built to close.

        Common Mix-Ups

        "A bigger context window removes the budget problem"

        • Right: cost and accuracy both depend on how many tokens you actually put into a given call, no matter how high that model's ceiling goes.
        • Wrong: thinking that switching to a model with a much larger window makes it fine to leave a tool that dumps a whole chapter as it is.
        • Why: the bill is for tokens sent, and the resent history keeps compounding every turn regardless of the ceiling; and context rot means a model can reason worse with a huge window full of mostly irrelevant tokens than with a small, curated one, so the fix is what you put in, not how large the window can go.

        "The context window holds the model's knowledge"

        • Right: the context window is only the text visible for this one call, the model's working memory for the request in front of it.
        • Wrong: believing that because a model "knows" facts from training, that training knowledge also sits in, or can be read out of, the context window.
        • Why: training knowledge is baked into the model's weights, separate from and far larger than any one request's window, and frozen at training time, which is why a chatbot can state an outdated fact with confidence (the first learning record). The context window holds only the live text sent and generated this call — nothing from training sits inside it.

          Section 2: What stays between steps, and what resets between sessions 9 min

          Learning goals
          • Tell apart accumulation within one session from the reset that happens between separate sessions.
          • Explain why nothing survives a new session unless something wrote it down outside the context window.
          • Decide, for a fact the assistant learns, whether it will still be visible next session without extra work.
          What you need to know first
          • The agent loop: the model is called repeatedly within one run until it gives a final answer or hits a limit, from the agent loop record.
          • Section 1 of this lesson: what the context window holds, and that everything in it is resent on every call within a session.

          The general idea

          Within one continuous session — a student keeps talking, or one agent run keeps looping — nothing is thrown away automatically. The system prompt, tools, and every message and tool result so far keep accumulating turn over turn (Anthropic, Effective context engineering for AI agents). This is the "between steps" case: each step's output becomes part of the input to the next step, exactly as Section 1's growing window showed.

          A session ends, though: the student closes the chat, or the agent run finishes. A new session later starts with a context window holding only whatever the harness puts into it this time. Nothing from the earlier session is automatically carried over — the context window itself resets, because it only ever held that one session's accumulated turns in the first place.

          So "remembering something across sessions" is never something the model does by itself; it is a deliberate choice in the program around the model. Either the fact already lives somewhere a tool can look it up again, such as a calendar or a training database, in which case the new session re-fetches it and it only looks like memory from the outside, or the fact existed only as text inside a conversation that is now gone, in which case it is genuinely lost unless an earlier session wrote it to storage that the new session reads back. That second case — writing something down on purpose — is "notes as memory," covered fully in Section 3.

          Important steps

          • At session end, ask which facts from this conversation live only in the chat text, versus which already live in a backing system a tool can query again.
          • For a fact that exists only as chat text and matters later, write it somewhere outside the context window before the session ends.
          • At the start of a new session, assume nothing carried over: either query the backing system again, or read back whatever was written for this purpose.

          Worked example: Monday's certification and Wednesday's booking

          The case

          On Monday, a student finishes the laser-cutter safety module during a chat with the assistant. Inside that one session, the assistant calls check_training_record, sees "not yet certified," walks the student through a quiz, and calls record_training_result, which marks them certified in the booking system's own database. All of Monday's back-and-forth — the quiz questions, the answers, the final result — stays in Monday's one growing context window for as long as that session runs.

          Why this idea applies here: the mission needs the assistant to remember each student's training status between visits, and visits are separate sessions. Whatever Monday's conversation "knows" is gone the moment that session ends, unless something it did persists outside that one context window.

          1. Identify what Monday's session actually changed in a backing system, versus what only exists as chat text: record_training_result wrote "certified: true" into the booking system's student record — that lives outside any context window, so it survives.
          2. Confirm nothing essential was left only in the conversation text: the quiz questions and answers don't need to survive, only the final certified status does, and that was written to the database, not left sitting unsaved in the chat.
          3. On Wednesday, in a new session, the assistant calls check_training_record again — not because it remembers Monday, but because the new session has no memory at all, and the only way to know the status is to ask the system that Monday's call wrote to.

          The result: Wednesday's assistant correctly says the student is certified, not through memory of Monday's chat, which is gone, but because Monday deliberately wrote the one fact that mattered into storage a later session could query again. Had record_training_result never run, Wednesday's assistant would have no way to know the student passed, however much the Monday conversation had covered.

          Common Mix-Ups

          "The assistant remembers me from last time"

          • Right: what looks like memory across visits is the harness re-querying a backing system, or reading back a note, at the start of the new session — never the model recalling the old conversation.
          • Wrong: assuming the model itself retains anything about a student between Monday's and Wednesday's sessions.
          • Why: each session gets its own fresh context window; Wednesday's call to check_training_record only works because Monday's session wrote "certified: true" somewhere outside any context window. Delete that database write, and Wednesday's assistant has no way to know what happened Monday, however detailed Monday's conversation was.

          "A longer conversation carries more forward to next time"

          • Right: how much a session discusses has no bearing on what survives to the next session; only what gets written to persistent storage survives.
          • Wrong: believing a longer, more thorough Monday conversation leaves Wednesday's assistant better informed than a short one would.
          • Why: a one-line Monday chat that calls record_training_result leaves Wednesday exactly as informed as a two-hour Monday chat that calls the same tool; an exhaustive Monday chat that never writes anything to storage leaves Wednesday with nothing, because length lives inside one session's context window, and that whole window disappears at session end regardless of its size.

            Section 3: Retrieval and notes as memory 9 min

            Learning goals
            • Explain just-in-time retrieval: keeping a pointer to a large source and pulling in only the relevant piece when it's needed.
            • Explain structured note-taking as a way to persist state across sessions.
            • Decide which of the two techniques fits a given piece of information the assistant handles.
            What you need to know first
            • Section 1 of this lesson: the context window's token budget, and why a large, irrelevant chunk is costly.
            • Section 2 of this lesson: nothing survives a new session unless it was written outside the context window.
            • Tool calling: the model requests a tool by name with arguments, and the program runs it and sends the result back as the next message; background from this workspace's earlier sessions.

            The general idea

            Section 1 showed that dumping a whole source into context is expensive and can hurt accuracy. Section 2 showed that nothing survives a new session by default. Retrieval and notes as memory are the two techniques that answer those two different problems, and keeping them separate matters, because reaching for the wrong one wastes effort.

            Retrieval, sometimes called just-in-time context loading, keeps a lightweight pointer to a large, mostly fixed source — file paths, a search index, a stored query — rather than the source's full text, and pulls in only the relevant slice through a tool call at the moment it is needed (Anthropic, Effective context engineering for AI agents). The source itself doesn't change session to session — a machine manual is a machine manual — so there is nothing to remember about it between visits; the only question each time is which part is relevant right now, and retrieval answers that fresh, on demand.

            Structured note-taking, also called agentic memory, is different: the agent itself writes a fact or a piece of state to a file or record living outside the context window, specifically so a later session can read it back (Claude Platform Docs, Memory tool). This fits information the agent generates or learns during a session, that changes over time, and that would otherwise exist only as chat text that disappears when the session ends — the certified-status flag from Section 2 is exactly this case.

            The two can combine: a note can itself hold a pointer used for retrieval later, such as "see manual chapter 4, section 2 for calibration," so the note stays small while still letting a later session fetch the full content again if it needs to.

            Important steps

            • Retrieval: keep an index or pointer to the source instead of its full text; query it at the moment a question needs it; pull back only the relevant slice, and re-query next time rather than keeping the slice around "just in case."
            • Notes as memory: decide, before a session ends, which facts must survive to the next one; write those facts outside the context window in a form a later session can read quickly; read the notes back at the start of the next session, and keep them updated rather than endlessly appended.

            Worked example: one question, two different fixes

            The case

            Mid-session, a student asks: "How do I calibrate the 3D printer bed, and do I still need to finish my safety module?" That single question needs two very different pieces of information: a stable fact buried in a 40-page printer manual, and a changing fact about one student that was established in an earlier session.

            Why this idea applies here: pulling the whole manual into context would waste most of the call's budget on irrelevant pages and risk the context rot from Section 1 for a question that needs one short section; and the model has no way to know the student's training status at all unless something persisted it from the earlier session, Section 2's problem. One question, two different fixes.

            1. Retrieval for the manual: search_manuals(query="3D printer bed calibration") runs a keyword search over an index built once, ahead of time, over the manual's chapters, and returns only the five-paragraph calibration section, about 180 tokens, instead of the full document, over 12,000 tokens. The manual hasn't changed since last week, so there's nothing to remember about it; it's searched fresh every time it's needed.
            2. Notes as memory for the student: check_training_record reads a stored note the booking system keeps per student, last updated when an earlier session called record_training_result after the student passed the safety quiz. That note is read back now because it was deliberately written to storage, outside any context window, so a later session could recover it without re-asking the student or re-running the quiz.
            3. Combine: the assistant answers the calibration question from the retrieved section, and the training question from what the note says, without ever loading the full manual or the full history of past conversations with this student.

            The result: the assistant answers both parts accurately and cheaply. The manual content came from retrieval because it is large, stable, and needed only in part; the training status came from a note because it is small, changes over time, and would never have existed anywhere else once Monday's session ended.

            Common Mix-Ups

            "Retrieval and notes as memory are the same technique"

            • Right: retrieval searches a large, mostly unchanging source for the relevant piece every time it's needed; notes as memory persists something the agent itself learned so a session can recover it without redoing the work that produced it.
            • Wrong: treating search_manuals and check_training_record as interchangeable because both are tool calls that bring information into context.
            • Why: the manual doesn't need anyone to write it down for next time; it's searched fresh each time because it hasn't changed. The training status does need to be written down, because it was established in a conversation that is otherwise gone the moment the session ends. Using retrieval for the training status, by re-asking the student every visit, or notes for the manual, by copying the whole book into a note, both miss why each technique exists.

            "Once retrieved, information is remembered"

            • Right: a retrieved chunk is only in context for the current session; it vanishes at session end, just like everything else in Section 2, unless it is separately written to a note.
            • Wrong: assuming that because the calibration section was pulled into context once, the assistant will "know" it next time without searching again.
            • Why: retrieval re-runs the search every time it's needed, specifically because nothing about the result is kept outside the context window. If a later session needs that section, search_manuals runs again; this is by design, not a limitation, since caching a stale copy would risk it going out of date after the manual is revised.

              Main points 2 min

              • The context window is the set of tokens a single model call can see: the system prompt, tool definitions, prior messages and tool results, and the output — not the model's training knowledge, and every token in it is paid for again on every later call in the same session.
              • A bigger context window doesn't remove the budget or quality problem: cost scales with tokens actually sent, and accuracy can degrade as irrelevant tokens pile up, a pattern called context rot.
              • Within one session, nothing is dropped automatically: each step's input is everything that came before it, growing every turn.
              • Between separate sessions, nothing carries over automatically: a new session's context window starts with only what the harness puts into it.
              • Retrieval keeps a pointer to a large, stable source and pulls in only the relevant slice on demand, so the source's full size never has to sit in context.
              • Notes as memory persist a fact the agent itself learned by writing it outside the context window so a later session can read it back; this is a deliberate design choice, not something the model does by itself.
