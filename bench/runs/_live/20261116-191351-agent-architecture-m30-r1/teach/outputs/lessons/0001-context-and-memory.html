          The context window and its cost 6 min

          Learning goals
          • Define a token and the context window.
          • List what fills the window in an agent.
          • Explain why a bigger window costs money and can lower quality.
          What you need to know first
          • A model takes text in and writes text out, from learning record 0001.
          • The agent loop, from learning record 0002.

          The general idea

          A token is the unit a model reads and writes: a word, part of a word, or a piece of punctuation. Text is cut into tokens before the model sees it, so everything is counted in tokens, not words. A long manual page can be thousands of tokens.

          The context window is everything the model can see and work with in one call, and its size is a limit counted in tokens (Claude docs: context windows). The model knows only two things: what it learned in training, and what is in the window. If a fact is in neither, the model cannot use it. That is why the window is the centre of agent design.

          In an agent the window holds several kinds of content at once:

          • The system prompt: your instructions for the assistant.
          • The tool descriptions: what each tool does and what it needs.
          • The conversation: the student's messages and the model's replies.
          • The tool results: calendar rows, manual pages, anything a tool returned.
          • The model's output, which also takes space in the window.

          Two consequences matter for your budget. First, you pay by the token, so a large window is not free space: each token you send costs money, and the output tokens are billed too. Second, more is not better. Anthropic's engineering team describes context rot: as the number of tokens grows, the model's ability to recall information from the context decreases, so context is a finite resource with diminishing returns (Effective context engineering for AI agents). The aim is the smallest set of useful tokens, not the largest.

          Window sizes differ by model and change over time, so check the current figure for the model you pick. Also check the price: the docs say requests over a certain size can be billed at a higher rate.

          Important steps

          • List every source of tokens in one call: system prompt, tool descriptions, history, tool results, output.
          • Estimate the size of each; the fixed parts repeat on every call.
          • Cut what the model does not need for this step.

          Worked example: what fills the makerspace assistant's window

          The case

          A student asks, "Is the laser cutter free Friday, and what material can I cut on it?" You are sizing one request. The numbers below are made up to show the method; you would measure your own.

          Why this idea applies here: your sponsor's budget is in tokens, and you cannot reduce what you have not listed.

          1. System prompt: about 800 tokens of rules (be brief, ask before booking).
          2. Three tool descriptions (calendar check, booking, manual search): about 1,200 tokens together.
          3. The question: about 30 tokens.
          4. A calendar result: about 400 tokens. A manual page for the laser cutter: about 3,000 tokens.
          5. The answer: about 200 tokens of output.

          The result: the manual page is the largest item by far, so it is the first place to look for savings. Loading a whole 40,000-token manual instead would make that one item ten times bigger than everything else combined, and would invite context rot.

          Common Mix-Ups

          "A bigger window means I can load everything"

          • Right: the window is a limit, and filling it costs money and can hurt recall.
          • Wrong: if the manuals fit, put them all in.
          • Why: every token is billed on every call, and context rot lowers recall as the window grows. A 40,000-token manual in every call is expensive and gives the model more to get lost in.

          "The window only holds my input"

          • Right: the model's output uses the same window.
          • Wrong: input and output are limited separately, so a full input is fine.
          • Why: a prompt that nearly fills the window leaves little room for the answer, which can then be cut short or rejected.

            What is kept between steps 7 min

            Learning goals
            • Explain why every step of the loop is a separate model call.
            • Describe what your program sends on each call.
            • Choose among clearing, compaction and trimming when the window fills.
            What you need to know first
            • The agent loop and that the program runs each tool, from learning record 0002.
            • The window and its parts, from Section 1.

            The general idea

            The model does not remember anything from one call to the next. Each call is independent: the model gets a window of text, writes a reply, and is done. What looks like memory inside a request is your program's work. It keeps a list of messages (the system prompt, the student's question, each model reply, each tool result) and sends the whole list again on every call.

            So one request with three steps is three calls, and each call sends a longer list than the one before. The new tool result is appended to the list, and the model reads everything again from the top. This is the part of the loop from learning record 0002 that matters for cost: the early tokens are paid for on every later call, so a big tool result costs you once for each step that follows it.

            A short request fits without trouble. A long task does not: the list grows until it nears the window limit, and quality may drop even before that. Three common responses, from lightest to heaviest:

            • Clearing: drop old tool results that are no longer needed, such as a manual page already used to answer.
            • Compaction: summarize the conversation near the limit and start a fresh window with the summary. Anthropic advises keeping what matters (decisions, open questions) and cutting redundant output (Effective context engineering).
            • Trimming: keep only the last few turns. It is simple, but it can drop a fact the student gave at the start.

            For the makerspace assistant most requests are short, so clearing a used manual page is usually enough.

            Important steps

            • Keep one message list in your program for the request.
            • After each tool call, append the model's tool request and the tool's result.
            • Send the whole list on the next call.
            • Before each call, check the size; clear, compact or trim if it nears your limit.

            Worked example: three calls for one booking request

            The case

            The student writes: "Book the laser cutter Friday at 2 and tell me the max material thickness." Numbers are illustrative: the fixed prompt and tools are 2,000 tokens.

            Why this idea applies here: to defend your cost estimate you must know that each call re-sends the earlier content.

            1. Call 1. Sent: 2,000 tokens. The model asks for the calendar tool (100 tokens). The program runs it and gets 400 tokens back.
            2. Call 2. Sent: 2,000 + 100 + 400 = 2,500 tokens. The model asks for a manual search (100 tokens). The result is 3,000 tokens.
            3. Call 3. Sent: 2,500 + 100 + 3,000 = 5,600 tokens. The model writes the final answer.

            The result: input tokens billed across the request are 2,000 + 2,500 + 5,600 = 10,100, although the final list holds only 5,600. If the manual page had been 30,000 tokens, call 3 alone would send 32,600. A rule follows: put big results as late as possible, and clear them once used.

            Common Mix-Ups

            "The model remembers its earlier steps"

            • Right: your program stores the steps and sends them again; the model sees them only because they are in the window.
            • Wrong: the model holds a running state between calls.
            • Why: if your program forgets to append the calendar result, the model in call 2 has no idea a calendar check happened and may ask for it again, adding steps and cost.

            "Cost is the size of the final context"

            • Right: cost adds up the input of every call.
            • Wrong: a request costs about what the last list weighs.
            • Why: in the example the final list is 5,600 tokens, but 10,100 input tokens were billed. More steps multiply this.
            Check Yourself

            An agent loop runs for 12 steps. Each step adds a 2,000-token tool result to the message list, starting from 1,000 tokens. Which statement about the cost is true?

              What is kept between sessions: notes 7 min

              Learning goals
              • Explain why the model keeps nothing between sessions.
              • Decide what to save, where, and who writes it.
              • Tell a saved note from a live lookup.
              What you need to know first
              • The window is emptied for each new call, from Section 1 and Section 2.
              • Reading JSON in Python, from your classes.

              The general idea

              A session is one conversation with a user, from its first message to its end. When it ends, the message list is gone. The next session starts with an empty window. The model's weights do not change from chatting, so it learns nothing from the old session.

              Memory between sessions is therefore a feature of your program. Structured note-taking is the technique where the agent regularly writes notes to storage outside the context window, and those notes are loaded back later (Effective context engineering). The storage can be a JSON file or a database table. What makes it memory is the step that puts the note back into the next window.

              Three design choices follow:

              • What to save. Save facts you will need again, in a small fixed shape: a student's ID, which machines they are trained on, the date. Do not save the whole transcript; it is large, and loading it costs tokens on every future session.
              • Who writes. Either the program writes the note when something happens (a training is recorded), or the model calls a "save note" tool. The first is more reliable for facts that matter, like training status.
              • When to read. Load the note at the start of a session, keyed by the student, and put it in the window. A small record costs a few tokens.

              Notes can go stale. A saved "laser cutter free Friday" is wrong by Saturday. Things that change should be looked up with a tool each time, and things that rarely change, like training status, can be saved.

              Important steps

              • Decide which facts need to survive the session, and keep them few.
              • Choose a shape for the note (fields, not prose) and a place to store it.
              • Write it when the fact changes, using code or a save tool.
              • Load it at the start of the next session, keyed by user.
              • Do not save what a live tool can fetch.

              Worked example: remembering training status

              The case

              Ana finished the laser cutter safety training on 3 March. On 10 March she returns and asks to book a laser cutter slot. The assistant must know she is trained without asking again.

              Why this idea applies here: the model has no memory of 3 March, and re-asking every student wastes time and tokens. A saved record solves both.

              1. When staff record the training, your program writes {"student": "ana01", "trained": ["laser"], "updated": "2025-03-03"} to a database row keyed by student.
              2. On 10 March, Ana signs in. The program reads her row, a few dozen tokens, and adds it to the system prompt: "Student training: laser."
              3. She asks to book. The model sees the line and calls the booking tool. A student with no row gets no such line, and the model is told to refuse equipment they are not trained on.
              4. Availability is not saved. The model calls the calendar tool on 10 March, because the calendar changes daily.

              The result: memory costs a few tokens per session, stays accurate because staff update it, and never has to be inferred by the model.

              Common Mix-Ups

              "The assistant remembers the student because it chatted with them"

              • Right: it "remembers" only what your program saved and loaded.
              • Wrong: the model learns from conversations and keeps what it learned.
              • Why: the weights are fixed after training. If the save step has a bug, the next session knows nothing, however friendly the earlier chat was.

              "Save the full transcript to be safe"

              • Right: save a small structured record of the facts needed later.
              • Wrong: a stored transcript is the best memory.
              • Why: loading old transcripts fills the window with irrelevant text, costs tokens on every session, and invites context rot. A ten-field record carries what matters.

                Retrieval: finding the right page 7 min

                Learning goals
                • Describe how chunking, indexing and search put the right passage in the window.
                • Tell keyword search from embedding search, and say when to combine them.
                • Explain why a chunk can lose its context, and how to fix it.
                What you need to know first
                • The window has a limit and a cost, from Section 1.
                • A tool call returns a result into the window, from Section 2.

                The general idea

                Retrieval means fetching only the pieces of a large source that a question needs and putting those into the window. It is a form of memory that holds more than the window can, and your manuals are a case: too long to include, and exact details matter. Anthropic describes agents loading data at runtime through tools rather than pre-loading everything, which it calls just-in-time retrieval (Effective context engineering). In your assistant, retrieval is simply a tool: search_manuals(query).

                Preparing the manuals takes two steps done ahead of time. Chunking splits each manual into passages, such as a section or a few paragraphs. Indexing stores them in a form that can be searched. At question time, the search returns the best few chunks, and only those enter the window.

                There are two main ways to search:

                • Keyword search (such as BM25) matches the words in the question to the words in chunks. It is strong for exact terms, like an error code "E-42" or a part name.
                • Embedding search turns text into lists of numbers, called embeddings, so that chunks with a similar meaning are close. It finds "the cutter will not turn on" when the manual says "power failure", which keyword search would miss.

                Each fails where the other works, so combining them is common. Anthropic also found that chunks lose context: a chunk saying "the machine must be cooled first" does not say which machine. Its Contextual Retrieval method prepends a short explanation of where the chunk sits before indexing. In its tests, the share of top-20 retrieval failures fell from 5.7% with embeddings alone to 2.9% with contextual embeddings plus contextual BM25 (Contextual Retrieval). These are their results on their data; test on yours.

                Important steps

                • Chunk each manual along its own structure (sections), and label each chunk with the machine and section.
                • Index the chunks for keyword search, embedding search, or both.
                • Expose search as a tool with a clear description.
                • Return the top few chunks, with their source, into the window.
                • Test with real student questions and check that the right chunk comes back.

                Worked example: "Why does the laser cutter show E-42?"

                The case

                The laser cutter manual runs 200 pages. A student asks, "My cutter shows E-42 and won't start. What do I do?" The answer is one paragraph on page 87, under "Cooling system faults".

                Why this idea applies here: loading 200 pages is costly and invites context rot; retrieval brings in just the paragraph that matters.

                1. Ahead of time, each section is a chunk, and each chunk gets the header "Laser cutter, Troubleshooting, Cooling system faults".
                2. The model calls search_manuals("laser cutter E-42").
                3. Keyword search finds the chunk that contains "E-42" exactly. Embedding search adds a chunk about coolant flow, since its meaning is close to "won't start".
                4. The program returns the top three chunks, about 1,500 tokens, with page numbers.
                5. The model answers from them and cites page 87, so the student can check.

                The result: about 1,500 tokens enter the window instead of the whole manual, and the answer is traceable to a page. Without the header, a chunk saying "check the coolant level" could belong to any machine.

                Common Mix-Ups

                "Embedding search is always better than keyword search"

                • Right: each wins on different questions, and combining them is common.
                • Wrong: meaning-based search makes exact keyword matching obsolete.
                • Why: an error code like E-42 has no useful "meaning" to match, and a similar code E-24 may rank close. Exact matching gets it right.

                "Retrieval means the model has read the manual"

                • Right: the model sees only the chunks returned for this question.
                • Wrong: once indexed, the manual is known to the model.
                • Why: if search returns the wrong chunk, the model has no other source and may answer wrongly with confidence. Retrieval quality limits answer quality, so test it.

                  Main points 2 min

                  • The context window is the limit, in tokens, on what the model sees and writes in one call; you pay for those tokens, and recall drops as the window fills.
                  • Fill it with the smallest useful set: system prompt, tool descriptions, history, tool results, output.
                  • The model keeps nothing between calls; your program resends the message list on every call, so early tokens are billed again at each step.
                  • When the list grows, clear old results, compact with a summary, or trim.
                  • Memory between sessions is data your program saves and loads: small structured notes, written reliably, read at session start.
                  • Save what is stable and needed again; look up what changes with a tool.
                  • Retrieval searches pre-chunked manuals and puts only the best few chunks in the window; it is a tool call.
                  • Combine keyword and embedding search, label chunks with their context, and test retrieval on real questions.
