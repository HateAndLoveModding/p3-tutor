Check your answer

The model is called and asks for a tool; the program runs the tool and sends the result back; the model is called again. The loop ends when the model writes a final answer instead of a tool request, or when a limit (such as a step cap) is reached. Today's question: what exactly does the model see each time it is called?

1. The context window 5 min

Learning goals
  • Define context and context window.
  • State what is inside the context at one model call.
  • Explain why every call re-sends the context, and what that does to cost.

The idea

Context is the set of tokens the model sees when it produces an output (Anthropic, Effective context engineering). A token is a chunk of text, often a word or part of one. The context window is the maximum number of tokens the model can take in per call, including the text it is about to write.

The model keeps nothing from one call to the next. Anything it should "know" at a step must be in the text the program sends at that step. For an agent, that text is built from these parts:

  • the system prompt (the assistant's role and rules);
  • the tool descriptions;
  • the conversation so far: the student's messages, the model's earlier tool requests, and the tool results.

Each loop step, the program appends the newest request and result and sends the whole list again. That is why you need two things before you begin:

  • You must already know: the agent loop, and that the program (not the model) runs tools.
  • You must already know: Python lists and dicts. The context is, in code, a list of messages.

Worked example: what the model sees at call 3

A student asks: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" Suppose the model has already called check_calendar and search_manuals, and is now being called a third time. Your program builds the input like this (simplified; real APIs use their own message format):

messages = [
  {"role": "user",      "content": "Is the laser cutter free tomorrow at 3 pm, and do I need training?"},
  {"role": "assistant", "content": "request: check_calendar(laser, tomorrow)"},
  {"role": "user",      "content": "result: free 2-4 pm"},
  {"role": "assistant", "content": "request: search_manuals('laser cutter training')"},
  {"role": "user",      "content": "result: 3 manual passages ..."},
]
reply = call_model(system=RULES, tools=TOOL_DESCRIPTIONS, messages=messages)

Why it works this way: the model has no stored copy of the earlier steps. The program re-sends them every time, and the model reads the list from the top. The memory tool's documentation describes the same pattern: the application runs each request and then sends the conversation back so Claude can continue (Claude docs: memory tool).

Cost follows directly. Model usage is priced by tokens, so a call that sends 2,980 tokens costs more than one that sends 1,530, and a 4-call request pays for the shared beginning of the context four times. Token counts are therefore your budget lever (the arithmetic is worked in section 5).

A common mix-up

Wrong: "The model remembers the earlier steps, so only the new result needs to be sent." Right: the model is called fresh each step, and the program re-sends everything it wants the model to see. Why it is tempting: a chat feels like a continuous conversation. What breaks: if your program sent only the training result at call 3, the model would not know what the student asked.

Check yourself

Your program is about to make the third model call of a request. What does it send?

Show the answer

The second option. Every call carries the full context; nothing is carried inside the model.

2. What is kept between steps 5 min

Learning goals
  • Explain how the context grows during one request.
  • Explain why a longer context is a cost problem and a quality problem.
  • Name two ways to shrink context during a long task: clearing old tool results and compaction.

The idea

Within one session, everything stays in the context until your program removes it. Each step adds the model's request and the tool's result, so the context only grows. Two problems follow:

  • Cost and the hard limit. Every later call re-sends everything earlier, and a context that passes the window limit cannot be sent.
  • Quality. Recall gets worse as the context grows, which Anthropic calls context rot, so context is a finite resource with diminishing marginal returns (Anthropic). A research study found that models answer best when the needed information is at the start or end of a long input and worse when it is in the middle (Liu et al., Lost in the Middle).

So the goal is the smallest set of high-signal tokens. Two standard tools, both done by your program:

  1. Clearing old tool results. Once the model has used a big result, delete it from the list. Anthropic describes this as a light form of compaction.
  2. Compaction. When the conversation nears the limit, summarize it and start a new window with the summary (Anthropic). Detail the summary drops is gone, so keep what matters for the task.
The makerspace assistant will usually finish a request in four or five steps, so you may never need compaction. It matters for long tasks, such as a coding agent working for an hour. Know it so you can say why you did not use it.

Worked example: one request, growing context

The student's request from section 1, with the numbers used in section 5. "In" is the tokens sent at that call.

CallWhat was added before itIn (tokens)
1Rules, tools, question (1,530)1,530
2+ calendar exchange (200)1,730
3+ manual passages (1,250)2,980
4+ training exchange (200)3,180

If the passages were not needed after call 3, clearing them would make call 4 cost about 1,930 tokens instead of 3,180. The model has already used them, and the answer on its way out does not need the raw text again.

A common mix-up

Wrong: "A bigger context window solves the problem, so I can keep everything." Right: a bigger window raises the limit, but you still pay for every token on every call, and recall still weakens as the context fills. Why it is tempting: "fits in the window" sounds like "will be used well". What breaks: a whole manual in the window can fit, and the model can still miss the one line that matters.

Check yourself

A research agent runs 30 steps. Each step calls a search tool that returns about 2,000 tokens, and the model only needs the facts from each result for the next step. What is the best first change to control cost and quality?

Show the answer

Clear old tool results. They are the bulk of the growing context and are no longer needed once used.

3. What is kept between sessions 6 min

Learning goals
  • State what survives when a session ends.
  • Explain how notes in a memory store work as memory.
  • Choose between a database record and a model-written note for a given fact.

The idea

A session is one run of the assistant for one student, from first message to last. When it ends, the context list is gone. When you call a model through its API, nothing else is saved for you: the model does not keep it, and the provider does not keep it for your app. Anything that must last must be written to storage that your program owns, and read back at the start of the next session.

That is the idea of memory for an agent: notes saved outside the context window, loaded back when needed. Anthropic calls it structured note-taking, where the agent regularly writes notes persisted to memory outside of the context window and reads them back later (Anthropic). Its memory tool follows this exactly:

  • The model asks to view, create, edit or delete files in a /memories directory.
  • Your application runs each request against storage you control and returns the result as a tool result.
  • A later session continues from the same memory because your handler serves the same store.

(Claude docs: memory tool.) Notice this is the agent loop you already know: a tool the model calls and your program runs. Memory is a tool, not a new mechanism.

Worked example: what to save for the makerspace

Your assistant should remember each student's training status. Two kinds of facts are involved, and they belong in different places (this is a design judgment, not a rule from a source):

  1. Exact facts others rely on, such as "Dana passed laser-cutter training on 3 March". A wrong answer here lets an untrained student use a machine. Store these in a record your program owns (a database or the makerspace's training list) and read them with a tool such as check_training_record. The model should never be the only keeper of this fact.
  2. Soft, helpful details, such as "Dana prefers morning slots and is working on a 3D-printed enclosure". These suit a short notes file the model writes and reads, so the next visit starts with the right context.

Why this split: a record is exact and checked; a note is flexible but only as reliable as what the model wrote. Whatever you store, load only what the current request needs, since loaded notes are context and cost tokens too.

The memory tool's documentation also lists your duties: validate every path so a request like /memories/../../secrets.env cannot escape the folder, cap file sizes, and delete stale files. Students' data adds a privacy duty: save only what the assistant needs.
A common mix-up

Wrong: "If I tell the model in the prompt to remember the student, it will." Right: an instruction does not create storage. Without a write to a store and a read in the next session, the fact is gone when the context is. Why it is tempting: chat products appear to remember you. What breaks: Dana returns next week, the new context has no record, and the assistant asks again whether she is trained.

Check yourself

Dana passed training in session 1. Next week she opens a new session. Under which condition does the assistant know she is trained?

Show the answer

Saved to storage and looked up in the new session. Persistence is your program's job.

4. Retrieval: finding the right page 6 min

Learning goals
  • Explain why you retrieve passages instead of putting a whole manual in context.
  • Describe the retrieval pipeline: split, index, search, return a few passages.
  • Explain just-in-time retrieval as a tool the model calls.

The idea

Retrieval means fetching only the pieces of a large source that are relevant to the current question and putting those pieces in context. It is the second way an agent gets information from outside the window: memory brings back what the agent saved, retrieval brings back what already exists, such as the machine manuals.

You need three ideas from earlier sections: context costs tokens on every call, recall weakens as context grows, and tools return text into the context.

The pipeline, in steps:

  1. Split each manual into chunks, such as a section or a few paragraphs, and keep each chunk's source and page number.
  2. Index the chunks so they can be searched. A keyword index matches the words used. An embedding index matches meaning, so "how fast to cut acrylic" can find a passage that says "feed rate for PMMA". Anthropic notes that many applications retrieve with embeddings (Anthropic).
  3. Search with the student's question and take the top few chunks.
  4. Return those chunks, with page numbers, into the context so the model answers from them and can cite them.

Where does the search run? Anthropic describes two timings. Many apps retrieve before the model runs. Agents can instead hold lightweight references and load data at runtime using tools, which is just-in-time retrieval: slower, but it keeps context focused (Anthropic). In your assistant, search_manuals(query) is exactly that: a tool the model calls when it decides it needs a manual passage, with the pipeline above behind it.

Retrieval is not perfect. If the search returns the wrong chunk, the model answers from the wrong chunk. Return page numbers so a student can check, and test the search on real student questions.

Worked example: finding the page on acrylic

A student asks, "What speed should I cut 3 mm acrylic at?" The manual is 300 pages. The model calls search_manuals("laser cutter speed 3 mm acrylic"). Your program searches the index and returns three chunks: the settings table for the laser cutter (page 47), a note on acrylic fumes (page 12) and a note on focus height (page 31), each marked with its page. The model reads about 1,200 tokens instead of the manual's roughly 40,000 (illustrative size). It answers with the speed from page 47 and cites it. Why retrieval fits here: the answer is local, one table, so loading 299 other pages adds only cost and noise.

A common mix-up

Wrong: "Retrieval means the model searches the manual by itself." Right: the model only writes a search request. Your program runs the search against an index you built and returns the chunks, like every other tool. Why it is tempting: the answer appears as if the model had read the manual. What breaks: if nobody built and tested the index, nothing is searched, and the model answers from whatever it already guessed.

Check yourself

The assistant must answer questions from a 300-page manual set. Which design best fits a small model budget?

Show the answer

Search an index per question and return a few labelled chunks.

5. Worked example: the cost of two designs 5 min

Learning goals
  • Total the input tokens of a multi-call request.
  • Use the total to compare two designs against a budget.

Method: each call's input is everything in the context at that call, so add each call's input and compare the totals. Numbers below are illustrative, not measured.

Worked example

Request: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" Rules and tool descriptions take 1,500 tokens, the question 30, each calendar or training exchange 200, and the manual 40,000.

  1. Design A: put the whole manual in the prompt. There is no search call, so there are three model calls (calendar, training, final answer). The starting context is 1,500 + 30 + 40,000 = 41,530.
  2. Call 1 sends 41,530. Call 2 adds the calendar exchange: 41,730. Call 3 adds the training exchange: 41,930.
  3. Total for A: 41,530 + 41,730 + 41,930 = 125,190 input tokens.
  4. Design B: search the manual. Four calls (calendar, search, training, final), with three retrieved passages worth 1,250 tokens including the request. This is the table in section 2: 1,530 + 1,730 + 2,980 + 3,180 = 9,420 input tokens.
  5. Compare: A is about 13 times B. B makes one more model call, but each call is far smaller, so it wins on cost, and its recall is likely better too.
Your turn

Your team changes Design B so the search returns ten passages of 400 tokens each, plus 50 tokens for the request, instead of three. Everything else is the same. First step given: call 1 still sends 1,530 and call 2 sends 1,730. Find the input for calls 3 and 4 and the new total.

Show a solution

Retrieved text: 10 × 400 + 50 = 4,050 tokens. Call 3: 1,730 + 4,050 = 5,780. Call 4 adds the training exchange: 5,780 + 200 = 5,980. Total: 1,530 + 1,730 + 5,780 + 5,980 = 15,020 input tokens, about 60% more than the 9,420 of the three-passage design. Retrieving more is not free: it costs on every later call in that request, so retrieve the fewest passages that reliably contain the answer.

Summary 1 min

  • Context is what the model sees at a call; the program rebuilds and re-sends it every step, so it grows and every token is paid for again.
  • Long contexts cost more and recall worse; clear old tool results and, for long tasks, compact.
  • Between sessions nothing survives unless your program saves it. Memory is notes in storage outside the window, written and read through tools.
  • Retrieval is a tool that fetches a few relevant chunks from a long source; exact facts belong in records, soft details in notes.
