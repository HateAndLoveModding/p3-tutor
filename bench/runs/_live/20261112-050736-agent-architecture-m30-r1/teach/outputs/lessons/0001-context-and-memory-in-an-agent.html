Context and memory in an agent

By the end of this lesson you can decide, for any piece of information in the makerspace assistant, whether it belongs in the context window, in saved notes, or in a searchable store, and say why.

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, on a small budget. Every one of those choices is a context or memory choice, and you will defend them at your design review.

Warm-up 2 min

Recall

In the agent loop, the model asks for a tool and the program runs it. What happens to the tool's result next? Answer from memory before you open the answer.

Check your answer

The program sends the result back to the model, which uses it to decide the next step: another tool request or the final answer. Today's question is what exactly is sent back each time, and how much of it the model can hold.

1. The context window: what the model sees 5 min

Learning goals
  • Define the context window and list what is in it.
  • Explain why the program must resend the history on every model call.
  • Say what is kept between steps and what is kept between sessions.

The general idea

The context window is all the text the model can look at when it writes a response, including the response itself. Anthropic's documentation calls it the model's "working memory", which is different from the training data ([Claude docs: context windows]). Everything in a request counts: the system prompt, every message including tool results, and the tool definitions (same source).

  • Between steps: the program keeps a list of all messages so far and sends the whole list on each model call. Each response and each tool result is appended. Previous turns are preserved completely (same source).
  • Between sessions: nothing is kept. A new session starts with a new, empty list unless your program loads something into it.

So "memory" in an agent is a design you build, not a property the model has. The model reads whatever the program puts in front of it, then writes the next piece.

Prerequisites:

  • The agent loop: model asks, program runs the tool, result returns (record 0002).
  • A token is a piece of text the model reads or writes (record 0001); window sizes are counted in tokens.

Worked example: one request, step by step

A student asks: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" The assistant answers in four model calls, as in quiz 0001's setup. The numbers below are illustrative assumptions, chosen to show the pattern, not measurements.

  • System prompt plus tool definitions: 1,500 tokens. The question: 50 tokens.
  • Each tool request the model writes: 50 tokens.
  • Results: search_manuals returns 3,000 tokens of manual text; check_calendar returns 400; check_training_record returns 100.
  1. Call 1 reads 1,550 tokens and requests search_manuals.
  2. Call 2 reads those 1,550, plus the 50-token request, plus the 3,000-token result: 4,600. It requests check_calendar.
  3. Call 3 reads 4,600 + 50 + 400 = 5,050 and requests check_training_record.
  4. Call 4 reads 5,050 + 50 + 100 = 5,200 and writes the final answer.

The model never "remembered" call 1 during call 2. The program handed it the text again. When the student closes the chat, the list is gone.

A common mix-up

Wrong: "The model remembers earlier steps and earlier chats by itself." Right: the model has no storage between calls; it sees only what is in the request. This is tempting because chatbots seem to remember. They do so because the app resends the earlier messages each turn. If your program sends nothing, the model knows nothing about last week's visit.

Check yourself

Your assistant finished a booking conversation with Sam on Monday. On Thursday Sam opens a new chat and asks, "Did you book my 3D printer slot?" The program sends only the system prompt and this new question. What happens?

Show the answer

The model cannot see Monday's chat. Only text in the current request is visible, so without a tool or saved notes it can only guess or admit it does not know.

2. What the context costs 5 min

Learning goals
  • Explain why a long history makes every later call more expensive.
  • Explain "context rot" and why more context is not automatically better.
  • Estimate the total input tokens of a multi-step request.

The general idea

Because the whole history is resent, you pay to process it again on every call. In the example, the model read 1,550 + 4,600 + 5,050 + 5,200 = 16,400 input tokens in total, although the longest single input was only 5,200. The manual text from call 2 was read three times.

  • Total input tokens grow faster than the history does: one big tool result is paid for on every later call.
  • Prompt caching can cut the price of repeated text, but cached text still occupies the window ([Claude docs]). Anthropic reports it can cut costs by up to 90% under its stated assumptions ([Contextual Retrieval]).

Size is also a quality problem. As the token count grows, accuracy and recall degrade, a phenomenon called context rot ([Claude docs]). Anthropic's engineering team describes an "attention budget" that every added token draws down, and recommends "the smallest possible set of high-signal tokens" that makes the desired outcome likely ([Effective context engineering]). Current models have windows up to 1M tokens, but that is a ceiling, not a target.

Prerequisite: the idea that the full history is resent each call (section 1).

Worked example: what would pasting every manual cost?

Suppose a teammate proposes putting a 40,000-token set of manuals in the system prompt, so no search tool is needed. Assume a typical request takes 4 calls.

  1. Every call carries the 40,000 manual tokens. Over 4 calls that is 160,000 input tokens before counting the question, tools or results.
  2. Compare with the search design: one 3,000-token result added at call 2 and read three times is 9,000 tokens.
  3. The manuals approach reads about 17 times more manual text per request, and the model must find the relevant page inside 40,000 tokens of unrelated machines.

The paste-everything approach is not wrong in every case: Anthropic notes knowledge bases under about 200,000 tokens (roughly 500 pages) can sometimes fit in a prompt without retrieval ([Contextual Retrieval]). But it is a cost and quality trade-off you must make on purpose.

A common mix-up

Wrong: "A 1M-token window means I can stop worrying about what goes in." Right: the window sets what fits, not what is wise. Each token is billed on every call and, past some point, makes the model's use of the rest less reliable. This is tempting because "fits" sounds like "works".

Check yourself

A request makes 5 model calls. A 2,000-token tool result arrives after call 1 and stays in the history. About how many input tokens does that one result add across the whole request?

Show the answer

8,000. Calls 2, 3, 4 and 5 each read the 2,000-token result, and call 1 came before it existed.

3. Keeping the context small 4 min

Learning goals
  • Name two ways to shrink a context that is getting full: clearing old tool results and compaction.
  • Choose between them for a given agent.

The general idea

  • Clearing tool results: remove old tool outputs the model no longer needs. Anthropic calls this a light-touch form of compaction ([Effective context engineering]); the API offers tool result clearing for agentic workflows ([Claude docs]).
  • Compaction: when a conversation nears the limit, summarize it and start a new window with the summary. Claude Code, for example, keeps architectural decisions and unresolved bugs and drops redundant tool output (same engineering post).

Both lose information. Compaction needs care in deciding what the summary keeps: first make sure it keeps everything important, then trim the rest.

Prerequisite: sections 1 and 2.

Worked example: which one for the makerspace assistant?

  1. Look at the shape of a request. Most end in 4 to 6 calls (assumption: check this once you log real requests). A few thousand tokens per call is far from any window limit.
  2. Find the bulk. The bulk is manual text from search_manuals. After the model has used a page to answer, that page is dead weight.
  3. Choose. Clearing old manual results is cheap and enough. Compaction is for long conversations; a student who chats for an hour about one project could need it, but that is not the typical request.
A common mix-up

Wrong: "Compaction is the same as memory between sessions." Right: compaction shrinks the context within one running conversation. Information that must survive into a different session has to be saved outside the window, which is the next section.

Check yourself

An agent researches a topic for hours, calling a search tool over 200 times. Early results are no longer needed, but its plan and findings so far are. What fits best?

Show the answer

Clear stale results and summarize plan and findings: remove what is no longer needed and carry forward what is.

4. Memory between sessions: notes and records 6 min

Learning goals
  • Explain how an agent keeps information across sessions by writing it outside the window.
  • Distinguish model-written notes from records your program loads.
  • Choose which one stores a given fact in the makerspace assistant.

The general idea

To survive a session ending, information must be written to storage outside the context window and read back into a later one. Anthropic calls the pattern structured note-taking: the agent writes notes to persistent storage and pulls them back later. Its example is Claude playing Pokémon, keeping tallies and maps across thousands of steps and rereading them after a context reset ([Effective context engineering]).

The Claude API's memory tool implements this as files under /memories. Claude requests file operations, and your application runs them against storage you control ([Claude docs: memory tool]). That is the same loop you know: the model asks, the program acts, the result comes back. Memory is a tool.

There are two ways to fill a later session's context:

Notes the model writesRecords your program loads
Who writes itThe model, through a memory toolYour code, from a database
Good forSoft facts: preferences, what was triedFacts that must be exact
RiskCan be wrong, stale or missingNeeds code to fetch and keep it current

The choice between them is design judgment, not something the documentation prescribes. The reasoning: a model-written note is only as reliable as what the model chose to write down.

Prerequisite: a tool is run by the program, not by the model (record 0002).

Worked example: Sam's training status

Sam completed laser cutter training on October 3. Sam also said they prefer afternoon slots. The assistant must act on both next week.

  1. Training status is an exact fact: wrong, and a student could run a machine untrained. Keep it in the training database and fetch it with check_training_record. The model never edits it.
  2. The afternoon preference is soft. A note in /memories is cheap, and a wrong note costs little.
  3. At the start of next week's session the program loads the notes into context, and the assistant calls check_training_record when the question needs it.
A common mix-up

Wrong: "Turning on a memory tool means the assistant reliably remembers everything about each student." Right: the model decides what to write, your code decides where it is stored, and notes can be stale or missing. Also, stored notes about students are personal data you are responsible for protecting; the docs say your application must validate paths and can cap file size and expire old files ([Claude docs: memory tool]).

Check yourself

Which fact is the best candidate for a model-written note rather than a record your program loads from a database?

Show the answer

The email-reminder preference: soft information where an error is cheap. The other four must be exact, so they belong in records your program controls.

5. Retrieval: finding the right page 6 min

Learning goals
  • Explain how a manual is split, indexed and searched so only a few pieces enter the context.
  • Contrast embedding search with keyword search, and say when each fails.
  • Describe how retrieval is exposed to an agent: as a tool.

The general idea

Retrieval means finding the few pieces of a large store that are relevant and putting only those in the context. The usual setup, called retrieval-augmented generation or RAG, has these steps ([Contextual Retrieval]):

  1. Chunk: split each manual into pieces of a few hundred tokens.
  2. Index: turn each chunk into an embedding, a vector of numbers that encodes its meaning, and store them so similar chunks can be found. Also build a keyword index with BM25, a ranking method that matches exact words.
  3. Search: at question time, find the best-matching chunks and return the top few.

The two search methods fail differently. Embeddings capture meaning but can miss exact matches such as an error code. BM25 finds exact strings, such as "TS-999", but not paraphrases ([Contextual Retrieval]). Using both is why Anthropic's approach combines them.

A second failure is lost context. A chunk like "The company's revenue grew by 3% over the previous quarter" names no company or period, so a search for one company's Q2 result misses it. Contextual retrieval prepends a short, generated description (usually 50 to 100 tokens) to each chunk before indexing. On Anthropic's own tests, the top-20 retrieval failure rate fell from 5.7% to 3.7% with contextual embeddings, to 2.9% adding contextual BM25, and to 1.9% adding reranking (same source). These are the vendor's measurements on its datasets, so test on your own manuals.

Finally, how does retrieval reach an agent? As a tool. Anthropic contrasts pre-retrieval (load data before the model runs) with just-in-time retrieval, where the agent keeps lightweight references and loads data through tools at runtime. It suggests a hybrid is often best, and notes just-in-time is slower and needs good tool guidance ([Effective context engineering]). The model decides when to call search_manuals, and your tool description tells it how.

Prerequisites: tools and their descriptions (record 0002); the cost of tokens (section 2).

Worked example: a chunk the plain index misses

A student asks, "What does the E-27 fault mean on the laser cutter?" Suppose the manual has the line "E-27: coolant flow low. Check the pump." in a chunk that begins mid-page.

  1. An embedding-only search may rank chunks about "laser problems" above the one that mentions E-27, since an error code carries little meaning.
  2. BM25 matches the exact string "E-27" and ranks the right chunk first.
  3. The chunk still does not say which machine it is about if the page header was cut off. A prepended line such as "From the Laser Cutter manual, error codes section" lets both indexes connect it to the question.
A common mix-up

Wrong: "Retrieval means the model reads the whole manual and picks the right page." Right: a search step outside the model picks a few chunks and only those enter the context. If the search misses the right chunk, the model never sees it, however capable it is. So a wrong answer can be a retrieval failure, not a reasoning failure.

Check yourself

Students ask exact part numbers like "PN-4471-B" and your embedding-only search often misses the right chunk. Which change most directly addresses this?

Show the answer

Add a keyword (BM25) index alongside the embeddings: exact strings like part numbers are what keyword matching is good at.

Worked example and practice 3 min

Worked example: sorting four items

For each item, decide: context (in the window now), record (loaded by the program), note (written by the model), or search (retrieved on demand).

  1. The assistant's rules and tool descriptions. Needed on every call: context, in the system prompt.
  2. The 3D printer manual, 300 pages. Large, and only a page or two matters per question: search.
  3. Whether Sam passed laser training. Must be exact: record.
  4. Sam prefers afternoons. Soft, cheap if wrong: note.
Your turn

Sort these three the same way, with a reason for each. First step: ask "does it need to be exact, and is it needed on every call?"

  • The calendar entries for the laser cutter tomorrow.
  • The tool result that returned the manual page about lens cleaning, after the model has already answered.
  • That Priya asked for a reminder before every booking.
Show a solution
  1. Calendar entries: exact and changing, so never save them. Fetch them with check_calendar when asked; they enter the context as a tool result.
  2. The used manual page: it was retrieved on demand and is now dead weight, so it is a candidate for clearing from the context (section 3).
  3. Priya's reminder request: a soft preference, so a note, loaded at the next session's start.

Summary 1 min

  • The context window is all the text the model sees on one call; the program resends the whole history every call, and nothing carries over to a new session unless you save and reload it.
  • A long history costs tokens on every later call and can reduce accuracy, so keep it small: clear stale results, compact when needed.
  • Between sessions, exact facts belong in records your program loads, soft facts in notes the model writes, and large documents in a searchable store.
  • Retrieval puts a few chunks in the context through a tool. Embeddings catch meaning, BM25 catches exact strings, and a retrieval miss cannot be fixed by the model.
