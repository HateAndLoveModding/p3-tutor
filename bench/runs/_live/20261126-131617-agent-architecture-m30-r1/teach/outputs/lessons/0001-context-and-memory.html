Context and memory: what your agent actually sees, and what it keeps

By the end of this lesson you can decide, for a real request to your makerspace assistant, what has to stay in the model's context, what disappears the moment a session ends, and how to give the assistant a memory that is bigger than its context window without paying to resend everything every time.

Objective O3: context, memory between sessions, and retrieval About 30 minutes Builds on the agent loop
Why this matters for you

Your assistant has to answer from machine manuals that run hundreds of pages and remember each student's training status from one visit to the next. Both of those are context and memory problems, not modeling problems, and your sponsor's small budget means every extra token you send has a real cost. Getting this wrong either makes the assistant expensive or makes it unsafe, by letting it forget who is actually certified to use a machine.

        1. The context window: what actually gets sent, in tokens 9 min

        Learning goals
        • Define a token and explain that the context window is measured in tokens, not words or messages.
        • Explain why the system prompt, the full history so far, and every tool result all count against the same limited budget, on every single call.
        • Trace how the number of tokens sent grows, call by call, across a multi-step run, and why that drives cost.
        What you need to know first
        • The agent loop: the model is called once per step, and each call is a separate request, not a continuation the model remembers on its own, from the agent loop.
        • A tool call and its result are text: the model asks for a tool by name with arguments, the program runs it, and the result comes back as text that becomes part of the model's next input.

        The general idea

        A token is the unit a model actually reads and is billed in: a short word, part of a longer word, a punctuation mark, or a piece of code, produced by splitting your text into the chunks the model was trained on (Anthropic, Token counting). A rough guide is about three tokens for every four English words, but the exact split depends on the text, so tools count tokens exactly rather than estimating from word counts.

        The context window is everything the model is given when it is asked to produce its next output: "the set of tokens included when sampling from a large-language model" (Anthropic, Effective context engineering for AI agents). For an agent, that bundle is not just the latest question. It is the system instructions, the whole conversation so far, and every tool call and tool result from every earlier step of the same run, because the model itself keeps nothing between calls: the only reason step four "knows" what happened at step one is that the program retypes it into step four's input.

        This has two consequences. First, the window has a hard size limit set by the model; once a run's history gets close to it, something has to change (Section 3 covers one option). Second, because every call resends the whole bundle so far, cost does not grow by a flat amount each step: it grows with the size of everything accumulated, since providers charge by the token for both what is sent in and what comes back. A run that keeps a 300-page manual sitting in its history is not paying for that manual once; it is paying for it again on every remaining step of that run.

        Important steps
        • At each call, the tokens sent equal: the system prompt, plus every earlier tool call and result in this run, plus the new input.
        • Tokens, not words and not messages, are what is capped and what is billed.
        • A long tool result does not cost once; it sits in history and gets resent, and paid for, on every later step of the same run.

        Worked example: tracing the token cost of one student request

        The case

        A student asks the assistant, "Is the laser cutter free tomorrow at 3pm, and do I need training to use it?" The assistant has a 300-token system prompt and two tools: check_calendar and check_training_record. It makes one tool call per step, then answers.

        Why this idea applies here: each of the four model calls in this run is a separate request, so to judge the cost of the whole run, you have to add up what is resent at every call, not just look at the size of the final answer.

        1. Call 1: system prompt (300 tokens) plus the student's question (25 tokens) = 325 tokens in. The model decides to call check_calendar.
        2. Call 2: everything from call 1 (325 tokens) plus the calendar tool's result, "free 1-5pm Tuesday" and similar (70 tokens) = 395 tokens in. The model decides to call check_training_record.
        3. Call 3: everything from call 2 (395 tokens) plus the training tool's result, the student's certification list (60 tokens) = 455 tokens in. The model now has what it needs and writes its final answer (40 tokens out).
        4. Total billed for the run: roughly 325 + 395 + 455 tokens in, plus the tokens generated at each step (two short tool requests and one final answer). The calendar result gets paid for twice (calls 2 and 3), and the system prompt gets paid for three times, once per call.

        The result: a two-tool request costs more than three times a single short message, not because any one call is expensive, but because the whole history is resent and re-billed at every step. With a small sponsor budget, this is why a design that lets tool results or old history pile up without limit is a cost risk, not just a tidiness problem.

        Common Mix-Ups

        "This call is cheap, I only sent one short question"

        • Right: the cost of a call depends on everything resent, which includes the system prompt and the full history of the run so far, not only the newest message.
        • Wrong: assuming a short new question means a cheap call.
        • Why: in the worked example, the student's new question each time is a few words, but call 3 still carries 455 tokens because the first two tool exchanges ride along. The visible new input is a poor guide to the actual bill.

        "A bigger context window solves the cost problem"

        • Right: the window's maximum size and the per-call cost are two separate limits; raising the maximum lets you fit more in, but every token you put in that fits still has to be paid for.
        • Wrong: treating a larger window as if it made large histories free.
        • Why: a bigger window would let the run in the worked example keep going for more steps before hitting a hard limit, but each of those extra steps would still re-bill the growing history; it raises the ceiling, not the price per token.
        Check Yourself

        By the start of its fourth call, your assistant's run has 900 tokens of accumulated history (system prompt plus three earlier tool exchanges). The third tool result, just added, was 600 tokens of that 900. The student's newest message adds 20 more tokens. Roughly how many tokens does call 4 send to the model?

          2. What survives: within a run, and between sessions 9 min

          Learning goals
          • Tell apart what stays available within one run, within one open chat session, and across sessions that have ended.
          • Explain why nothing carries over to the next session unless a program explicitly writes it outside the context window and reads it back in.
          • Spot the belief that a model keeps its own standing memory of past conversations, and say why it is wrong.
          What you need to know first
          • Section 1: every call resends the system prompt and the full history of the run, including every tool result so far.
          • The agent loop ends with a final answer or a stopping condition, from the agent loop.

          The general idea

          Section 1 showed that within one run, every step's tool result stays available because the program keeps retyping it into each new call. That is the only "memory" happening inside a run, and it is not stored anywhere in the model; it exists purely because the program keeps resending it as text. The same mechanism explains a long chat: if a conversation stretches over many user turns, each new turn gets appended to a growing transcript that is resent in full, which is why the assistant can refer back to something said ten messages ago in the same open chat.

          That mechanism stops the moment a session ends, whether because the chat window closes, the student walks away, or the program restarts. The context window for that run is simply gone. The model holds nothing back for later: it has no notion of "earlier today" or "yesterday" once the text that described it is no longer being sent to it. Anything that needs to be true in a future session has to be deliberately written to storage outside the context window, and deliberately read back into context at the start of the next session; Anthropic describes this as writing notes "persisted to memory outside of the context window" so they can be "pulled back into the context window at later times" (Anthropic, Effective context engineering for AI agents).

          This is exactly where the misconception from your first quiz applies: believing an agent has "automatic memory of every earlier conversation" is wrong both as a definition of what makes something an agent and as a description of how memory actually works. Nothing is automatic. A session that feels coherent is resending text within itself; a new session starts from nothing unless someone built the save-and-reload step on purpose.

          Important steps
          • At the end of a session, ask: is there a fact here that must still be true in a future session?
          • If yes, the program writes that fact to storage (a file, a database row) before the session's context is discarded.
          • At the start of the next session, the program reads the specific fact needed and inserts it into the new context, before the model answers.
          • Keep what gets reloaded small and specific; reloading an entire past transcript defeats the point, and Section 3 covers how to keep it small.

          Worked example: Jordan's laser cutter certification, Monday to Tuesday

          The case

          On Monday, Jordan chats with the assistant, takes the laser cutter safety quiz through a tool call, and passes. The session then ends. On Tuesday, a new session starts, and someone asks whether Jordan is cleared to use the laser cutter.

          Why this idea applies here: this spans two separate sessions, so the only way Tuesday's assistant can know about Monday's result is if something was written outside Monday's context window and is read back in on Tuesday; otherwise this is a safety problem, since an uncertified student could be treated as certified, or the reverse.

          1. Without a save step: Monday's session ends, and its context, including the quiz result, is discarded along with everything else in that run. Tuesday's session starts with none of it; the assistant has to say it does not know, or worse, guesses.
          2. With a save step: at the end of Monday's session, the program writes a small fact to storage outside the context window, such as a row in a students.json file: {"student": "Jordan", "cert": "laser_cutter", "date": "2026-11-23"}. This write happens because the program was built to do it, not automatically.
          3. With a load step: before Tuesday's session answers a question about Jordan, the program looks up Jordan's row and inserts a short line into the new context, such as "Jordan is certified for: laser cutter (as of 2026-11-23)," before the model is asked anything.

          The result: only the write-then-read pair makes Tuesday's answer correct. The fact did not persist because it was important; it persisted because two separate pieces of code were written to make it persist.

          Common Mix-Ups

          "The model remembers earlier conversations on its own"

          • Right: a model has no standing memory between sessions; what looks like memory within one long chat is the whole transcript being resent on every turn of that same session.
          • Wrong: believing the model itself recalls Jordan's quiz result on Tuesday because it "talked to" Jordan on Monday.
          • Why: Monday's session and Tuesday's session are different runs with different context windows; nothing links them unless a program reads a saved fact into Tuesday's window, as this section's example shows.

          "Important facts save themselves"

          • Right: a fact persists only because specific code writes it to storage and specific code reads it back in; there is no default behavior that detects "this mattered" and keeps it.
          • Wrong: assuming that because Jordan's certification is obviously important, the system will have kept it somewhere.
          • Why: without the write step in the worked example, Monday's result is discarded exactly like everything else in that session, regardless of how important it was to someone reading the conversation.

            3. Retrieval and notes: a memory bigger than the window 9 min

            Learning goals
            • Explain why pasting a whole manual library into context on every call is both too expensive and too large.
            • Explain retrieval: indexing documents, searching for the relevant piece, and injecting only that piece into context.
            • Explain notes: a small, explicitly written and reloaded fact, and tell it apart from retrieval over a large, mostly fixed document set.
            What you need to know first
            • Section 1: the context window has a size limit, and every token sent costs money, so stuffing in everything "just in case" is expensive.
            • Section 2: nothing survives between sessions unless it is explicitly written to storage and explicitly read back in.

            The general idea

            Put the two prior sections together and the makerspace assistant has two different problems. The machine manuals are long, mostly fixed documents that already exist in full; the context window cannot hold all of them on every call, and even if it could, Section 1 showed that doing so would re-bill the whole manual on every remaining step. Meanwhile, a student's training status is not a document anywhere; it is a fact that only exists because something happened in a past session, and Section 2 showed that it only survives if something writes it down and reads it back.

            Retrieval solves the first problem: break the manuals into smaller chunks, build a searchable index over them ahead of time, and at question time, search for the chunks that best match the question, then put only those chunks into context for that call. AWS describes this as converting documents into a searchable store and, when a question comes in, matching it against that store and injecting "the relevant retrieved data in context" before the model answers (AWS, What is Retrieval-Augmented Generation?). The manual itself never has to sit in context; only the one relevant paragraph does, for the one call that needs it.

            Notes solve the second problem, and they are a different thing from retrieval, not a variant of it: a note is a short fact the system itself writes down as it is learned, such as "Jordan: certified laser cutter, 2026-11-23," kept "persisted to memory outside of the context window" and reloaded only "at later times" when it is relevant (Anthropic, Effective context engineering for AI agents). Retrieval searches a large, pre-existing body of text; a note is produced by the system itself, from something that happened, and there is no document to search until the note is written. Both keep the context window small by living outside it and entering only when needed, which is what gives the assistant a memory far bigger than any one context window.

            Important steps
            • Sort what the assistant needs into documents to index (manuals, procedures) and facts to note (per-student or per-booking state that only exists because of something that happened).
            • For retrieval: chunk the documents, index them, search using the current question, and inject only the top matching chunk or chunks.
            • For notes: after something worth remembering happens, write a short, specific fact to storage; before a later call that needs it, read just that fact back into context, not an entire file or transcript.

            Worked example: one question, two sources of context

            The case

            A student asks, "How do I clean the lens on the laser cutter, and am I cleared to use it?" Answering well needs two different things: a procedure from a 300-page manual, and a fact about this specific student.

            Why this idea applies here: the manual is a large, fixed document that already exists in full, which calls for retrieval; the student's clearance is a fact about ongoing state that was recorded earlier, which calls for a note. Treating both the same way, by either searching the student record or trying to paste in the whole manual, would not work.

            1. Retrieval step: the manual was chunked and indexed in advance. The program searches that index with "clean lens laser cutter" and gets back the one paragraph describing the cleaning procedure, which is injected into this call's context.
            2. Notes step: the program looks up this student's row in the saved student records (the same kind of store built in Section 2) and injects one line, "cleared for: laser cutter," into the same call's context.
            3. Model call: the model now has the system prompt, the student's question, one manual paragraph, and one status line, not the whole manual and not the whole student history, and can answer both parts.

            The result: the call stays small and cheap no matter how large the manual library or the student roster grows, because both the manual and the roster live outside the context window and only the small, relevant piece of each is pulled in for this one question.

            Common Mix-Ups

            "Retrieval means the assistant is searching the internet"

            • Right: retrieval searches an index you built over your own documents, such as the makerspace's manuals, not the open web.
            • Wrong: assuming "search" always means a live web search.
            • Why: the manual chunk in the worked example comes from an index of files the makerspace controls; nothing leaves that index, which is also why the answer can be trusted to match your actual equipment rather than a generic result from somewhere else.

            "If you have retrieval, you don't need notes"

            • Right: retrieval only works over text that already exists as a document; a student's live clearance status is not a pre-existing document, so it has to be recorded as a note when it happens before it can be found at all.
            • Wrong: expecting a search system to "find" Jordan's Monday certification the way it finds a page in the manual.
            • Why: in the worked example, there is no manual page that says Jordan is certified; that fact exists only because Section 2's save step wrote it down. Retrieval and notes solve different problems and are both needed here.

            Which of these is the better fit for retrieval rather than a note: searching the 3D printer's troubleshooting guide for "nozzle clogged," or recording that a specific student finished the 3D printer orientation today?

              Main points 1 min

              • The context window is everything sent to the model on one call, measured in tokens: the system prompt, the full history of the run so far, and every tool result, all resent in full on every call.
              • Cost grows with the accumulated history, not just the newest message, because providers bill by the token for everything sent and generated.
              • Within one run or one open session, history "persists" only because the program keeps retyping it into each new call; the model itself stores nothing between calls.
              • Nothing survives from one session to the next unless a program explicitly writes a fact to storage outside the context window and explicitly reads it back in at the start of the next session; this is never automatic.
              • Retrieval answers from large, mostly fixed documents (like manuals) by indexing them and injecting only the chunks that match the current question, instead of loading the whole document every call.
              • Notes answer the "remember this across visits" problem for facts that are not documents, by writing a short, specific fact when it happens and reloading just that fact when it is next needed.
