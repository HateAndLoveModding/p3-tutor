1. The context window 6 min

Learning goals
  • Define the context window and list what is inside it.
  • Explain why a bigger window does not mean you should fill it.

The general idea

The context window is all the text the model can reference when it writes a response, including the response itself. Anthropic's docs describe it as the model's "working memory", which is different from the data it was trained on (Claude docs: Context windows). The model has nothing else to work from: if a fact is not in the window, the model cannot use it.

Everything in the request counts toward the window:

  • the system prompt (your instructions),
  • the tool definitions (the names and descriptions you wrote),
  • every message so far, including tool results,
  • and the output the model writes.

Windows are measured in tokens, the small pieces of text a model reads and writes; a token is roughly a short word or part of a word. Current Claude models offer windows of up to 1M tokens (Claude docs). You pay per token sent and written, so every token in the context is also a cost.

Prior knowledge you need:

  • The agent loop: one model call per step (learning record 0002).
  • A model takes text in and writes text out (learning record 0001).

Worked example: what the makerspace assistant sees

A student asks, "Can I use the laser cutter tomorrow at 3 pm?" For the first model call, the program builds the window from your system prompt ("You are the makerspace assistant..."), the definitions of check_calendar, search_manuals and book_machine, and the question. Say that is 3,000 tokens (an illustrative number). Why this matters: the 3,000 tokens are there on every call, whether or not they are needed, so a short system prompt and short, clear tool descriptions save money on every request.

The window also has a quality limit. Anthropic's engineering team describes context rot: as the number of tokens grows, the model's ability to recall information from the context decreases, because the model has a finite "attention budget" that each new token draws down (Effective context engineering for AI agents). The goal is the smallest set of high-signal tokens that gets the job done.

A common mix-up

Wrong: "A 1M-token window means I can paste in all the manuals and be done." Why it is tempting: if the text fits, it seems the model has it. What is true: fitting is not the same as working well. Recall degrades as the window fills, and you pay for every token on every call. A large window is room, not a reason to fill it.

Check yourself

Your assistant's tool descriptions total 4,000 tokens, and a teammate proposes adding six more long tools "just in case". What is the main cost of this?

Show the answer

Extra tokens on every call, and more for the model to sort through. Tool definitions are part of the context on every request, so they cost tokens each time.

2. What is kept between steps 6 min

Learning goals
  • Explain that the model keeps nothing between calls and the program resends the history.
  • Estimate how input tokens grow across the steps of one request.
  • Name two ways to shrink a long history: clearing old tool results and compaction.

The general idea

Each step of the agent loop is a separate model call, and the model itself keeps nothing between calls. What looks like memory within a conversation is the program resending the history: each turn's input is "all previous conversation history plus the current user message", and the output becomes part of the next input (Claude docs). Tool results are part of that history.

The consequence for cost: the call at step 5 pays again for everything from steps 1 to 4. Input tokens summed over a request grow faster than the number of steps.

Steps to estimate it:

  1. Start with the first call's input: system prompt, tools and question.
  2. Add to it, after each step, the model's tool request plus the tool's result.
  3. The input of each call is the starting size plus everything added so far.
  4. Sum the inputs of all calls.
Worked example

The assistant starts with 3,000 tokens. The manual search returns a long page, so each tool step adds 2,000 tokens (request plus result). The request needs three tool steps, then the final answer, so four model calls.

  1. Call 1 reads 3,000 tokens.
  2. Call 2 reads 3,000 + 2,000 = 5,000.
  3. Call 3 reads 5,000 + 2,000 = 7,000.
  4. Call 4 reads 7,000 + 2,000 = 9,000.
  5. Total input tokens: 3,000 + 5,000 + 7,000 + 9,000 = 24,000. That is eight times the 3,000 that the first call costs, from only three added steps.

Why we care: a budget-limited team must count per request, not per step, and long tool results are the fastest way to inflate it. (Real services may bill cached input at a lower rate; see the prompt caching docs. Caching changes what you pay for those tokens, not whether they count toward the window.)

Shrinking a long history

  • Clearing old tool results: after the model has used a manual page, drop the page text and keep a short line saying what was found. Anthropic's guidance is that clearing old tool results is a light, safe first step (context engineering post); the API offers it as context editing.
  • Compaction: when a conversation nears the window limit, summarize it and continue with the summary. The risk is that the summary drops a detail you needed later, so you check what it keeps (server-side compaction).

For the makerspace assistant, most requests are short (a few steps), so clearing a large manual page after use is usually enough. Compaction matters for long chats.

A common mix-up

Wrong: "The model remembers step 1 when it gets to step 4." Why it is tempting: the final answer refers to earlier steps. What is true: it refers to them because the program put them in the window again. If your program forgot to send the calendar result, the model at step 3 would not know it existed.

Check yourself

A request starts at 2,000 tokens, adds 1,000 tokens per tool step, and has two tool steps before the final answer (three model calls). How many input tokens in total across the request?

Show the answer

9,000 tokens: call 1 reads 2,000, call 2 reads 3,000, call 3 reads 4,000.

3. What is kept between sessions: notes 6 min

Learning goals
  • Explain why a new session starts with an empty context.
  • Describe notes as memory that lives outside the context window.
  • Decide what the assistant should write down and when it reads it back.

The general idea

A session is one conversation: one history that the program resends. When the student closes the chat and returns next week, the program starts a new history, and the window is empty. Nothing from last week is there, because the model keeps nothing and the old history was not sent.

To remember across sessions, the agent needs notes (also called agentic memory): information saved outside the context window, in a file or database, and loaded back when needed. Anthropic describes this as the agent regularly writing notes "persisted to memory outside of the context window" and pulling them back in later (context engineering post). Claude also offers a memory tool built on this idea.

Notes are ordinary program features, with three decisions to make:

  • What to save: small facts that matter later and that cannot be looked up elsewhere. Not whole transcripts.
  • When to write: as a tool the model calls (save_note) or as code that runs after an event such as a completed training. For facts that must be right, code from a trusted record is safer than the model's own say-so.
  • When to read: at the start of a session the program loads the student's record into the context, or the model calls a get_student_record tool.
Worked example: training status

Sam completes laser cutter training on Monday. On Thursday, in a new chat, Sam asks to book it.

  1. On Monday, the training system writes a record: {"student": "sam", "certified": ["laser_cutter"], "date": "Mon"}. Why: it is a small fact, it must be correct, and it will be needed months later.
  2. On Thursday, the session starts with an empty context. The program looks up Sam's record by login and adds one line to the context: "Sam is certified on: laser_cutter." Why: the model cannot ask for what it does not know exists, so the program loads what every request needs.
  3. Sam asks to book the laser cutter. The model sees the certification, calls check_calendar, then book_machine. A request for the 3D printer would find no certification, and the assistant would explain the training needed.

Cost: about 20 tokens of notes instead of replaying Monday's whole chat, which could be thousands.

A common mix-up

Wrong: "A larger context window, or compaction, gives the assistant memory across visits." Why it is tempting: both are called memory in casual talk. What is true: both only manage what is in one session's window. When the session ends, the window is gone. Saving between sessions needs storage outside the window, plus a step that loads it back.

Check yourself

The assistant saves, after each chat, a model-written summary of the whole conversation as Sam's "record", and next visit loads it. Which problem is most likely?

Show the answer

The summary may lose or distort the one fact needed. Prefer small structured facts written from a trusted source.

4. Retrieval from long documents 7 min

Learning goals
  • Explain retrieval and when to use it instead of loading everything.
  • Describe chunking, embeddings and keyword search and what each is good at.
  • Say who does the retrieving in an agent: a tool the program runs.

The general idea

Retrieval means fetching only the relevant pieces of a large body of text and putting them in the context for the model to use. Anthropic describes retrieval-augmented generation (RAG) as retrieving relevant information from a knowledge base and appending it to the user's prompt (Contextual Retrieval).

First check whether you need it. That article notes that if your knowledge base is under about 200,000 tokens (about 500 pages), you can put all of it in the prompt, and prompt caching makes this cheaper and faster. Beyond that, or when each call must stay small, use retrieval.

A typical setup:

  1. Chunk the manuals ahead of time: split them into pieces of up to a few hundred tokens.
  2. Index the chunks two ways. An embedding turns each chunk into a list of numbers that represents its meaning, so a search finds chunks with similar meaning to the question. BM25 is keyword search that matches exact words, which suits codes and part names.
  3. At question time, search the index and return the best few chunks.
  4. Put those chunks, not the whole manual, in the context.

The two searches fail differently: embeddings can miss an exact code such as an error number, and BM25 can miss a question worded differently from the manual (Contextual Retrieval). Using both is called hybrid search.

In an agent, retrieval is just a tool. search_manuals(query) is run by your program, which returns a few chunks as the tool result. Anthropic's term for the agent fetching what it needs at run time, through lightweight references and tools, is just-in-time retrieval (context engineering post).

Worked example: error code E-42

A student asks, "My 3D printer says E-42. What do I do?" The manual set is 2,000 pages, far over the size to include whole.

  1. The model calls search_manuals("3D printer error E-42"). Why a tool: the model cannot see the manuals; it can only ask.
  2. The program runs both searches. BM25 finds the chunk containing the exact string "E-42". Embedding search returns general troubleshooting chunks. Why both: the exact code needs keyword matching; a vague question like "printer stops mid-print" needs meaning matching.
  3. The program merges the results and returns the top three chunks, about 900 tokens in total, as the tool result.
  4. The model answers from the E-42 chunk. The chunk is now in the history for the rest of the session, and after use it can be cleared (section 2).
A common mix-up

Wrong: "The model searches the manuals itself." Why it is tempting: the answer appears to come from the manual. What is true: the model only writes a search request. Your program runs the search, and the quality of the answer depends on whether the right chunk was returned. If the chunk is not retrieved, the model does not have it, and may answer anyway from general patterns, so test your retrieval before blaming the model.

Check yourself

Your manuals total 150,000 tokens, and nearly every question needs a manual. Which choice does the lesson's source support as reasonable?

Show the answer

Summary 2 min

  • The model sees only the context window: system prompt, tools, history and its own output. Every token costs money, and more tokens can mean worse recall.
  • Within a session, the program resends the history on every call, so input tokens add up quickly; clear old tool results or compact.
  • Between sessions, nothing is kept unless you save it outside the window (notes) and load it back.
  • For long documents, chunk and index them, and let a search tool return only a few chunks; use keyword plus meaning search.

Say it in your own words: without looking, explain to a teammate why the assistant knows about the calendar result at step 3, but does not know Sam's training next week unless you build something.
