Context and memory in an agent

By the end of this lesson you can say exactly what your makerspace assistant sees at each step, what it forgets between visits, and which of three tools (the context window, saved notes, retrieval) to use for each thing it must know.

The context window: what the model sees 5 min

Start with a concrete case. A student types: "Can I cut 6 mm acrylic on the laser cutter?" Before your program calls the model, it builds one long piece of text out of several parts:

  • the system prompt: your instructions ("You are the makerspace assistant. Never book a machine for a student who lacks training.");
  • the tool descriptions: the names, purposes and parameters of check_calendar, search_manuals and the rest;
  • the conversation so far: the student's messages, the model's earlier replies and tool requests, and the tool results.

All of that, together, is the context: the text the model is given on one call. The model reads it and writes the next piece. The context is the only thing the model has to work with on that call: it has no other view of the world. The context window is the limit on how much context fits in one call, counted in tokens. A token is a chunk of text the model reads and writes, roughly a short word or part of a longer one. The limit covers what goes in and what the model writes out.

Two things follow, and your design depends on both.

It is finite, and bigger is not free. Anthropic's engineering team describes context as a finite resource with diminishing marginal returns, and says models have an "attention budget" that each added token draws down. They also describe context rot: as the number of tokens in the window grows, the model's ability to recall information from it decreases, to differing degrees in different models (Anthropic, Effective context engineering for AI agents). So a full window is not just expensive; it is a worse place for the model to find the one fact that matters.

You pay for it. Model usage is billed by tokens, and the input to each call is the whole context. This is the link to your sponsor's budget, and the next section shows how fast it adds up.

A common mix-up

"If the window is big enough, I can stop thinking about what goes in it." It is tempting because the numbers on model pages keep growing. But a window that can hold every manual is not a reason to put them there: every call re-reads and re-bills all of it, and per the context rot finding, recall of any one detail can get worse as the window fills. Window size sets the ceiling; curating the context sets the quality and the cost.

Between steps: the transcript grows 6 min

Now connect this to the loop you already know. In the quiz on the agent loop, every step is a separate model call. Here is the consequence for memory: the model does not carry anything from one call to the next. What carries the earlier steps forward is your program, which keeps the transcript (the running list of messages, tool requests and tool results) and sends all of it again on the next call.

Follow one request: "Is the laser cutter free tomorrow at 3 pm, and do I need training?"

  1. Call 1. The input is the system prompt, the tool descriptions and the question. The model writes a request for check_calendar.
  2. The program runs the tool and appends the request and the result to the transcript.
  3. Call 2. The input is everything from call 1, plus the request and the calendar result. The model writes a request for search_manuals.
  4. This repeats. Each call's input is the previous call's input plus what was just added.

This has three practical effects.

  • Cost grows faster than the number of steps. You pay input tokens on every call, and each call's input is larger than the last. A long manual excerpt returned at step 3 is paid for again at step 4, step 5 and so on.
  • Big tool results are the usual culprit. The fixed prefix is predictable; one search that returns ten pages is not.
  • The model "remembers" a step only because the text is still in the transcript. There is no hidden memory inside it.
Some providers can cache a prompt prefix that repeats, so re-reading it costs less. Anthropic's write-up on retrieval says prompt caching cut cost by up to 90% in its example (Anthropic, Contextual Retrieval). Check your provider's pricing before you count on it; the lesson's point stands either way: what you put in the context is what you pay to re-read.
Check yourself

Your assistant is on step 6 of a request. A tool result from step 2 was a 3,000-token manual excerpt that is no longer needed. What is true of it?

Show the answer

It is still sent and billed on every later call. The program owns the transcript, so clearing old results is the program's job. Anthropic calls clearing old tool results one of the safest forms of compaction (source).

Between sessions: nothing is kept 4 min

A session is one conversation, from the first message to the last. When a student closes the chat and returns on Thursday, your program starts a new transcript. The model on Thursday is the same model as on Monday, and it has no record of Monday: the transcript lived in your program's variables, and the model never stored it.

A common mix-up

"The assistant learns from each conversation, so it will know me next time." You may have seen chatbot products that appear to remember you. When they do, it is because the product saves something and loads it into the context at the start of a later chat. It is a feature someone built, not something the model does by itself. The model's training does not change during your conversation.

So for the makerspace assistant, "remember each student's training status" means three jobs for your code:

  1. Save the fact somewhere outside the model, such as a database row or a file.
  2. Load it when the student returns, or give the model a tool that looks it up.
  3. Decide what is worth saving at all.

Notice that training status is exactly the kind of fact you already have a reliable record for. In many designs the best "memory" is simply a tool, like check_training_record, over a record the makerspace already keeps, not a clever memory feature. That is cheaper, easier to correct, and easier to defend at a review.

Notes and compaction: memory you build 5 min

Two techniques extend what an agent can keep. Both come from Anthropic's guide to context engineering, which describes techniques for long tasks (source).

Notes: write it down, outside the window

Structured note-taking means the agent regularly writes notes to storage outside the context window, and reads them back when needed. The guide's examples are a to-do list and a NOTES.md file, and it describes a Claude agent playing Pokémon that kept progress notes so it could continue after its context was reset. The same idea works for a student: after a booking, the assistant writes one line to the student's file.

student: alex_m
training: laser_cutter (done 2026-10-12), 3d_printer (not yet)
preferences: prefers morning slots
last_booking: laser_cutter, Fri 14:00

At the start of the next session, your program loads this file into the context: about 40 tokens, instead of replaying a whole old transcript. The difference between notes and a transcript is that notes are chosen. Someone (you, or the model through a tool) decided what mattered.

Compaction: summarize when the window fills

Compaction means taking a conversation that is nearing the context limit, summarizing it, and starting a fresh window with the summary. It keeps one long task going within one session. The guide advises first making sure the summary captures everything important (recall), then trimming what is unneeded (precision), and notes that clearing old tool results is one of the lightest forms.

The trade-off

Anything you save, summarize or drop is a decision about what the assistant can no longer see. A summary can lose a detail that turns out to matter, such as the student's exact deadline. For facts that must be exact, like training status, save the structured value, not a prose summary of it.

Check yourself

A booking conversation has run for 90 messages and is close to the window limit, but the student is still choosing between slots. Which technique fits this problem?

Show the answer

Compaction. The window is filling within one session. (Notes might be a sensible add-on for the next visit, but they do not fix this one.)

Retrieval: finding the right page 6 min

Now the manuals. Suppose the laser cutter manual is 200 pages and the full set of machine manuals is far larger. A student asks, "What's the maximum thickness of acrylic I can cut?" The answer is in one paragraph on one page. You do not want to put 200 pages in the context on every call, for the reasons you now know: cost and context rot.

Retrieval means searching a collection for the few pieces relevant to the question and putting only those into the context. When the retrieved text is added to the model's input so it can answer from it, the pattern is often called retrieval-augmented generation, or RAG. Here is how the classic version works, as Anthropic describes it (Anthropic, Introducing Contextual Retrieval):

  1. Chunk. Split each document into small pieces, usually no more than a few hundred tokens.
  2. Index. Convert each chunk into a vector (an embedding, a list of numbers that encodes its meaning) and store it, so chunks can be found by similarity of meaning. Many systems also keep a word-matching index called BM25, which is good at exact terms such as an error code or a part number, where meaning-based search may miss.
  3. Search. At question time, find the top few chunks, then put those into the context.

You can do the search two ways. In up-front retrieval your program searches before the model call and inserts the chunks. In just-in-time retrieval, the model is given a tool such as search_manuals(query) and decides when and what to search. This is the version in your loop. Anthropic notes the trade: runtime exploration is slower than retrieving pre-computed data, and many setups mix both, such as loading a small file up front and searching for the rest as needed.

Where retrieval fails: the chunk that lost its label

Anthropic's example is a chunk that says revenue "grew by 3% over the previous quarter." Alone, it does not say which company or which quarter, so search cannot match it to a question about that company. The makerspace version: a chunk reading "Maximum material thickness: 6 mm" does not say it is about the laser cutter, and the vacuum former manual has a similar line. A search for "laser cutter acrylic thickness" can miss the right chunk or return the wrong one.

The fix Anthropic describes is to prepend a short, chunk-specific explanation of where the chunk comes from before indexing it. In their tests, this contextual retrieval reduced the failure to find the right chunks (in the top 20) by 35% with embeddings alone, by 49% when combined with BM25, and by 67% with reranking added (source). For a student project, the cheap version is the same idea done by hand: put the machine name and section title at the top of every chunk.

A common mix-up

"Retrieval means the model reads the whole manual and picks out the answer." It is tempting because the end result looks like that. In fact the model never sees the whole manual: the search picks a few chunks before the model reads anything. If the search misses the right chunk, the model cannot use it, and may answer anyway from training. This is why retrieval quality, not model size, is often what limits answers from manuals.

One more design option for you: the same Anthropic post says that if a knowledge base is under about 200,000 tokens (roughly 500 pages), you can often put it all in the prompt and skip retrieval, with prompt caching to keep it fast and cheap. Compare that with your total manual size before you build an index.
Check yourself

The assistant gives the wrong thickness limit for the laser cutter. You find that the correct chunk exists in the index but was not among the chunks returned. What is the most likely cause?

Show the answer

The search missed it. The model only works with what is retrieved, so a missing chunk is a retrieval failure, and unlabeled chunks are a common cause.

Worked example and practice 8 min

Worked example: what does one request cost in input tokens?

The assistant has a system prompt of 800 tokens and tool descriptions of 1,200 tokens. The student's question is 50 tokens. It makes three tool calls and then answers. Each tool request the model writes is 50 tokens. The results are: calendar 300 tokens, manual search 1,500 tokens, training record 100 tokens. How many input tokens in total across all four model calls? (Ignore the output tokens of the final answer.)

  1. Call 1 input = system prompt + tools + question = 800 + 1,200 + 50 = 2,050. The reason: nothing else is in the transcript yet.
  2. Call 2 input = call 1 input + the model's request (50) + calendar result (300) = 2,400. The reason: the whole transcript is re-sent, with the new items on the end.
  3. Call 3 input = 2,400 + 50 + 1,500 = 3,950. The manual result joins the transcript.
  4. Call 4 input = 3,950 + 50 + 100 = 4,100. The model now has what it needs to write the final answer.
  5. Total = 2,050 + 2,400 + 3,950 + 4,100 = 12,500 input tokens, although the whole request adds only 2,050 tokens beyond the 2,050 you start with (the final transcript is 4,100 tokens). Re-reading is what costs.
Your turn

You change search_manuals so that it returns the top 3 chunks of 200 tokens each (600 tokens) instead of 1,500. Everything else is the same. Step 1 is done for you: call 1 still costs 2,050 and call 2 still costs 2,400. Work out calls 3 and 4, then the total, and say how many tokens you saved.

Show a solution
  1. Call 3 input = 2,400 + 50 + 600 = 3,050.
  2. Call 4 input = 3,050 + 50 + 100 = 3,200.
  3. Total = 2,050 + 2,400 + 3,050 + 3,200 = 10,700 input tokens.
  4. Saved = 12,500 − 10,700 = 1,800. That is 900 fewer tokens in each of the two calls (3 and 4) that carry the search result.

The lesson for your design: shrinking a result that stays in the transcript saves its size multiplied by the number of later calls that re-send it.

Show a model answer
  1. Context. It is needed on every call of this request and costs almost nothing.
  2. Saved notes (or a training-record tool). It must survive between sessions and be exact.
  3. Retrieval. It is in a long document, needed only when asked, and should be loaded only then.
  4. Context. It is short-lived working state for this session; after the booking, only the result (the booking) needs saving.

Your rule of thumb: this request, in the context; across visits, saved; long reference material, retrieved.

Summary 2 min

  • The context is the text sent on one call; the context window is its size limit. Bigger windows cost more and recall can degrade as they fill (context rot).
  • Between steps, the program re-sends the whole transcript every call, so cost grows with each result you leave in it.
  • Between sessions, the model keeps nothing; memory is a save step plus a load step you build, using notes for exact facts and compaction for long tasks.
  • Retrieval finds a few relevant chunks in a long document before the model reads anything; its main failure is missing the right chunk.
