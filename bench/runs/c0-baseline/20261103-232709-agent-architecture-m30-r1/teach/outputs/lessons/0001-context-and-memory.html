Context and memory in an agent

By the end of this lesson you can say what the makerspace assistant sees at each step, what it keeps between steps and between students' visits, and how it finds the right page in a long manual.

Objective O3: context and memory in an agent About 30 minutes Builds on: the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status. Both jobs are memory problems, and both cost money, because everything the model reads is billed. This lesson gives you the vocabulary and the three design choices for your design review: what stays in context, what is saved, and how pages are found.

Check your answer

The program runs the tool. It then sends the result back to the model as part of the model's next input, and calls the model again. That "next input" is today's topic: what exactly is in it, and what happens as it grows?

The context window: everything the model sees 5 min

Start with a concrete request. A student types: "Can I use the laser cutter on Friday afternoon? I finished training last month." The assistant has a booking tool and a manual-search tool.

The model is called for the first time. What does the program hand it? Not just the question. It hands over a bundle of text:

  • the system prompt: the standing instructions you wrote ("You are the makerspace assistant. Be brief. Never book without confirming.");
  • the tool definitions: the name, description and parameters of each tool;
  • the conversation so far: the student's messages and the model's earlier replies;
  • the tool results that have come back during this request.

All of this together is the context window: the text the model can refer to when it writes its next output, including the output itself. Anthropic's documentation calls it the model's "working memory" and says it is different from the large body of text the model was trained on (Claude docs: context windows). Everything in the request counts toward it: the system prompt, every message, tool results, tool definitions, and the output the model writes.

Text is measured in tokens: small pieces of text, often a short word or part of a longer one. A page of manual might be 500 to 800 tokens. You do not need exact counts; you need to know that tokens are what the window limits and what you pay for.

This is the key fact for the rest of the lesson. The model does not keep anything from one call to the next. The program keeps the list of messages and sends the whole list each time. Anthropic's documentation describes it this way: each turn's input contains "all previous conversation history plus the current user message," and the model's output becomes part of the input for the next turn (Claude docs).

An everyday comparison: a call with a friend who has no memory. Before every sentence you read them the full transcript of the conversation so far. They answer well, because the transcript is right there, but if you leave out a line, for them it never happened.

A common mix-up

"The assistant remembers what we talked about, so it must store it somewhere inside the model." It is tempting because chat apps feel continuous. But what feels like memory is the program re-sending the transcript. If the program does not include a message, the model cannot use it. This is why you, the designer, decide what the model knows at every step.

Why more context is not better 5 min

If the whole stack is re-sent on every call, two problems appear as it grows: it costs more, and the model gets worse at using it.

Cost: you pay for the whole stack every call

Providers bill by tokens read and tokens written. Because call 3 re-reads everything from calls 1 and 2, the total tokens read across a request is much larger than the final size of the window. A made-up but realistic example for your assistant:

  • system prompt + tool definitions + the question: 2,500 tokens;
  • each tool call the model writes: about 100 tokens;
  • each manual page returned by the search tool: 3,000 tokens.
CallWhat it readsTokens read
1prompt, tools, question2,500
2call 1 + tool call + page A5,600
3call 2 + tool call + page B8,700
Total read across the request16,800

The window at call 3 holds 8,700 tokens, yet the request read 16,800. Every extra page you keep in context is re-read, and billed, on every later call. For a small budget, this is the biggest lever you have, bigger than which question the student asks. (Anthropic notes that prompt caching changes what you pay for repeated tokens, not whether they count toward the window; see the same page.)

Quality: the window is not a perfect memory

Modern windows are large: Anthropic's documentation lists up to 1 million tokens for current models. That is room for thousands of pages. So why not paste in every manual? Because of context rot: as the number of tokens grows, the model's accuracy and recall of information in the window decline. The docs conclude that "curating what's in context [is] just as important as how much space is available" (Claude docs). Anthropic's engineering team describes the window as an "attention budget": each token you add spends some of it, and the goal is "the smallest possible set of high-signal tokens" that gets the job done (Effective context engineering for AI agents).

Window sizes change quickly between models. Check the docs page when you pick one; the design principle, curate rather than stuff, does not change.
A common mix-up

"The window is huge now, so I can put all the manuals in and skip retrieval." Even if it fits, you pay to re-read it on every call, and the model finds details in a crowded window less reliably than in a short, focused one. Fitting is not the same as working well.

Between steps: what stays, what goes 6 min

Within one request (the loop from the agent-loop session), the default is to keep everything. That default is simple and it works for short requests. For long ones you need a policy. Anthropic's context-engineering article describes the main options (source):

Tool result clearing
Drop old tool outputs the agent no longer needs. The model keeps a record that it called the tool, but the bulky page text is gone. It is the lightest option, and the Claude docs list it under context editing.
Compaction
When the conversation nears the limit, have the model summarize it and start a fresh window containing the summary. Key decisions and open problems are kept; redundant output is dropped. The cost is that detail the summary left out is lost.
Sub-agents
A helper with its own clean window does a focused job, such as searching a manual, and returns only a short summary. The lead agent never sees the pages. (Whether this pays off is a later lesson.)

A rule of thumb for your assistant: a booking confirmation must survive, because it is a decision. The text of a manual page the model already used to answer is a good candidate to clear. Ask of each item, "will a later step need this exact text?"

Between sessions: notes as memory 6 min

Now the second kind of memory. A student finishes a chat on Monday. On Thursday they start a new one. What does the model know about them? Based on Section 1, you can predict it: nothing, unless the program puts it into the new window. A new session starts with an empty message list. Whatever the window held on Monday is gone.

So anything that must survive between sessions has to be saved outside the window, by the program, and loaded back in. Anthropic's article calls this structured note-taking, or agentic memory: the agent regularly writes notes that are persisted outside the context window and are pulled back in later (source). In plain terms, notes are a file or database row, and memory is the act of reading them into the window.

Worked idea: the training-status record

For the makerspace, the memory that matters is small and factual:

student: riley
laser_cutter_training: completed 2026-10-03
3d_printer_training: not completed
preference: afternoon slots

On Thursday, the program looks up riley, and adds those four lines to the system prompt or the first message. The model now behaves as if it remembers. It does not remember; it has been told, and the cost is about 40 tokens.

Three design questions for any memory

QuestionFor the makerspace
What is worth saving?Facts a later session needs: training status, preferences. Not the full chat.
Who writes it?Safety-critical facts (training status) should come from the official record, not from something the model inferred in chat. A model can write notes for low-stakes things.
When is it loaded?At session start for small facts; on demand if the notes grow large.

Notice the second row. A student who says "I did the training last week" has made a claim, not a record. If the assistant saves that as a note and trusts it, a safety rule has been bypassed by a sentence. Memory is only as reliable as what writes it.

Anthropic's API has a memory tool that lets the model read and write files in a folder you control, so notes survive between sessions. It is linked from the context-window docs page; read it when you build, not before the design review.
A common mix-up

"The assistant will remember Riley's training if it was told once in a chat." It was told in a window, and windows end. Unless something saved the fact and a later session loaded it, the next session starts blank. Chat apps that appear to remember are doing this saving and loading behind the scenes.

Retrieval: finding the right page 6 min

The third piece of memory is the manuals themselves. A laser cutter manual might run to 200 pages. Section 2 told us not to paste it all into the window. So how does the model find the right page? With retrieval: fetching only the pieces relevant to the question and placing just those into the window.

Two timings

Anthropic's article names two approaches (source):

  • Up-front retrieval: before the model is called, the program searches (often with embeddings, which find text with a similar meaning) and puts the best matches in the window. It is fast, one model call, and simple.
  • Just-in-time retrieval: the model holds light pointers, such as file names or stored queries, and uses tools to load data when it decides it needs it. It adapts to the question, at the price of extra loop steps.

The article describes a hybrid as often best: load a little up front for speed, then let the agent explore. It says Claude Code works this way, loading a notes file up front and using search tools to fetch files as needed.

A concrete case

Question: "What's the maximum material thickness for the laser cutter?" A good retrieval path:

  1. Split each manual into chunks (a section or a few paragraphs each), and index them ahead of time.
  2. Search the index with the student's question; take the top few chunks.
  3. Put only those chunks into the window, labelled with manual and page, and have the model answer with the page cited.

Cost: perhaps 1,500 tokens of chunks instead of 200 pages. Quality: a short, focused window, with a citation the student can check.

One known weakness: a chunk cut from the middle of a manual can lose its meaning. A chunk that says "The limit is 6 mm" does not say which machine or material. Anthropic's contextual retrieval post addresses this by adding a short explanation of where each chunk comes from before indexing it, and reports that this lowered the rate of failed retrievals (by 35% alone, 49% combined with keyword search, in their tests). A cheap version for you: start every chunk with the machine name and section title.

Worked example and practice 5 min

Worked example

Student Dana asks: "Book me the 3D printer for tomorrow at 2." Decide what is in context, what is saved and what is retrieved.

  1. Saved notes, loaded at start. The program looks up Dana's record: 3D printer training "not completed". Reason: this is a safety fact from the official record, loaded into the window as about 40 tokens.
  2. Context. The window holds the system prompt, tool definitions, Dana's message and the notes line. The model reads the notes and sees that booking is not allowed yet.
  3. Retrieval, if needed. Dana asks how to get trained. The model searches the manual index, receives two short chunks about the training sign-up, and answers with their page numbers.
  4. After the answer. Clear the retrieved chunks, since the question is resolved. Save one new note only if the official system records something new, such as a sign-up.
Your turn

Same setup as Section 2: 2,500 tokens to start, 100 per tool call, 3,000 per returned page. A request needs four model calls: three tool calls (each returning a page) and a final answer. Step one is given: call 1 reads 2,500 tokens. Work out the tokens read by calls 2, 3 and 4, then the total across the request.

Show a solution

Call 2 reads 2,500 + 100 + 3,000 = 5,600. Call 3 reads 5,600 + 100 + 3,000 = 8,700. Call 4 reads 8,700 + 100 + 3,000 = 11,800. Total: 2,500 + 5,600 + 8,700 + 11,800 = 28,600 tokens. Now notice: if you cleared old pages and kept only the newest, calls 3 and 4 would each read about 5,600 tokens instead, which is where the savings in a long request come from.

Summary 2 min

  • The context window is everything the model sees in one call. The program re-sends it each call; the model keeps nothing itself.
  • A growing window costs more (it is re-read each call) and works worse (context rot), so curate it: clear used tool results, compact when near the limit.
  • Between sessions, nothing survives unless it was saved outside the window and loaded back in. Save short, reliable facts.
  • Long manuals stay outside the window; retrieval brings in only the relevant chunks, up front, just in time, or both.
