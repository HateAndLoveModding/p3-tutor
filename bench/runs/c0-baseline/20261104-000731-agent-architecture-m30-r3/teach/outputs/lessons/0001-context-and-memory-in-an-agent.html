Warm-up 3 min

Last time you traced a request through the agent loop. Before we add memory, pull that loop back out of your head.

Recall

A student asks, "Is the laser cutter free tomorrow at 3 pm?" The assistant has a calendar tool. Without looking back: who actually runs the tool, the model or the program around it? And after it runs, what happens to the result?

Check your answer

The program runs the tool. The model only writes a request that names the tool and its arguments. The program then puts the result back in front of the model and calls the model again, so every step of the loop is a separate model call.

That last point is the doorway to today: if each step is a separate call, what the model "remembers" from one step to the next is only whatever the program sends it again.

The context window: what the model sees 5 min

Start with an everyday picture. You are on the phone with a helpdesk agent who has no computer and no notes. Everything they can use to answer you is what you say during this call, plus the script on the desk in front of them. When the call ends, they forget it all.

A language model is in that position. Its context window is all the text the model can use when it writes a response, including the response itself. It is like a working memory, and it is separate from what the model absorbed in training (Claude docs: context windows).

Text is measured in tokens, small pieces of text, roughly a short word or part of a longer one. The window has a limit in tokens, and so does your bill: providers charge per token sent in and written out.

What is in the window

For an agent, the window holds more than the chat. According to the docs, everything in the request counts: the system prompt, every message including tool results, your tool definitions, and the output the model writes (Claude docs). For your assistant, that is:

  • the system prompt: the standing instructions ("You are the makerspace assistant. Never book a machine without confirming training.");
  • the tool descriptions: the names and descriptions of check_calendar, search_manuals and the rest, which is how the model knows they exist;
  • the conversation: the student's messages and the model's replies;
  • the tool calls and tool results: each request the model made and what came back.

The model does not remember; the program re-sends

Here is the idea that most changes how you design. The model keeps nothing between calls. For a chat to feel continuous, your program sends the whole history again with each new call. The docs describe each turn as an input phase that contains all previous conversation history plus the new message, and the output then becomes part of the input for the next turn (Claude docs).

So "memory" in a basic assistant is a Python list that your code keeps and re-sends. If that list is lost, so is the memory. Since you have written Python before, you can picture it: messages = [], then messages.append(...) after every message and every tool result, and the whole list goes out on every call.

A common mix-up

"The model learns from our conversation, so it will know this student next time." It is tempting because chat feels like talking to a person who remembers. But a conversation does not change the model; it only adds text to the window for that run. Training is what changes a model, and training is out of scope for your project. If the assistant should know something next week, your program has to save it and put it back in the window.

Check yourself

Your assistant's code sends the model a call, gets a reply, and then your program crashes and restarts. The restarted program starts a new empty messages list. What can the model say about the earlier conversation?

Show the answer

Nothing. The model only sees what is in the request. If the new list is empty, the old conversation is gone unless your program saved it somewhere and loads it back.

Between steps: everything piles up 7 min

Now combine the re-sending idea with the agent loop. Inside one request, each step is a separate model call, and each call carries the entire history so far: the original question, every tool request and every tool result. The window only grows as the loop runs, until something removes text from it.

Worked numbers: how one request grows

Take the question from your earlier work, now with two parts: "Is the laser cutter free tomorrow at 3 pm, and do I need training to use it?" These token counts are illustrative, in the right size range but not measured:

CallWhat is added just before itAddedWindow size (tokens sent)
1System prompt, tool descriptions, student question1,5501,550
2Model's calendar request (60) + calendar result (300)3601,910
3Model's search request (60) + one manual page (1,500)1,5603,470
4Model's training request (60) + training record (200)2603,730

The final window is 3,730 tokens, but the number of tokens you pay to send is the sum over all four calls: 1,550 + 1,910 + 3,470 + 3,730 = 10,660. The early text is paid for again at every step. Prompt caching can lower the price of re-sent text, but the docs are clear that cached tokens still occupy the context window; caching changes what you pay, not whether they count (Claude docs).

Notice where the growth comes from: tool results. A manual page is five times the size of everything else added in the whole run. In a real run with more steps and bigger results, tool output is usually what fills the window.

Why a fuller window is not a better window

Modern windows are large; the docs list a 1M-token window for many current models. It is tempting to conclude that you can put everything in and stop designing. The docs push back: more context is not automatically better, because as token count grows, accuracy and recall degrade, a phenomenon called context rot, which makes curating what is in context as important as how much room there is (Claude docs).

Anthropic's engineers describe context as a finite "attention budget" and give a rule of thumb: find the smallest set of high-signal tokens that makes the result you want likely (Effective context engineering for AI agents). An older research paper found a related effect: models answered best when the relevant passage was at the start or end of a long input and worse when it was in the middle (Lost in the Middle).

That paper tested earlier models, so treat it as evidence for the general risk, not as a measurement of any model you will use. Test your own assistant on your own manuals.

So there are two reasons to keep the window lean: cost (you pay for every token, at every step) and quality (a crowded window is a worse working memory).

What can be done when the window fills

The same Anthropic article lists three moves for long runs (Effective context engineering):

  • Clearing old tool results: once the model has used a manual page, drop the page and keep the model's note of what it learned. The article calls this one of the lightest forms of compaction.
  • Compaction: when the window nears its limit, summarize the conversation and start a new window from the summary.
  • Sub-agents: a helper works in its own fresh window and hands back a short summary. We leave this for the lesson on multi-agent systems.
Check yourself

Your assistant answers a long question with 8 steps, and each step returns a 2,000-token manual excerpt. Which design change cuts the cost most without hurting the answer?

Show the answer

Clearing used excerpts. By step 8 you would be re-sending up to 14,000 tokens of old excerpts; clearing them after use keeps the window near its starting size.

Between sessions: nothing is kept unless you keep it 6 min

A session here means one conversation, from the student's first message until it ends. When the next one starts, the window is empty again. The student told the assistant on Monday that they finished laser-cutter training; on Thursday, a fresh session knows nothing about it.

Compare a mechanic's shop. The mechanic does not remember every car. They keep a job card for each customer, read it when the car comes in, and write on it before it leaves. That card is what we mean by notes as memory: information the agent writes to storage outside the window, then reads back later.

Anthropic describes exactly this as structured note-taking, also called agentic memory: the agent regularly writes notes to persistent storage outside the context window and pulls them back in later. Their examples include a to-do list and a custom agent that keeps a NOTES.md file, and they note that after a context reset the agent reads its notes and carries on (Effective context engineering). The Claude platform also offers a file-based memory tool for this (memory tool docs).

Notes or compaction?

Both help with long work, but they answer different questions:

CompactionNotes
What it isA summary of the current conversationFacts written to storage on purpose
Who decides what is keptA summarizing step, near the limitThe agent or your code, as it goes
Survives a new sessionOnly if you also save the summaryYes, that is the point
Best forOne long back-and-forthFacts needed on a later visit

Anthropic's guidance matches: compaction suits tasks with a lot of back-and-forth, note-taking suits work with clear milestones (Effective context engineering). A student's training status is a clear fact, so it belongs in notes, not in a summary that might drop it.

A common mix-up

"Save the whole transcript, and the assistant will remember everything." Saving is easy, but loading it all back refills the window with old chatter, which costs tokens at every step and adds noise. Memory is useful when it is small and specific: "Riley: laser cutter trained 3 Oct; 3D printer not trained." Write down facts, not conversations.

One more design point: notes are only as good as the program around them. The model does not read your notes on its own. Either your code loads the notes into the system prompt at the start of a session, or you give the model a tool such as read_student_notes(student_id) and describe it well, so the model knows when to call it. A note nobody loads is the same as no note.

Retrieval: finding the right page 6 min

Your second problem is the manuals. Suppose each manual is 40 pages at about 500 tokens a page, so 20,000 tokens, and you have 12 machines. All manuals together are about 240,000 tokens. Pasting them into the system prompt means sending 240,000 tokens at every one of the four calls in our example, nearly a million tokens for one question, plus the crowded-window quality risk from earlier.

Retrieval means fetching only the few pieces that are relevant to the question and putting just those in the window. It is how you find the right page in a long manual, as you would use a book's index instead of rereading the book.

How a search finds the page

First, split each manual into chunks, passages of a few paragraphs, ideally cut along headings so a chunk is one self-contained topic. Then a search ranks the chunks against the student's question. Two common ways:

  • Keyword search: matches the words. It finds "kerf" if the student typed "kerf", but may miss "how wide is the cut".
  • Embedding search: an embedding is a list of numbers that stands for the meaning of a text, built so that texts about similar things get similar numbers. The question and each chunk are converted, and the closest chunks win. It can match "how wide is the cut" to the kerf section.

Many systems combine both. That choice is a design review topic for you, and the lesson on workflows will return to it.

Up front, or when the agent asks

Anthropic describes two timings (Effective context engineering):

  • Up-front retrieval: the program searches before the model is called, using the student's question, and puts the best chunks in the first request. Simple and fast: one call may be enough.
  • Just-in-time retrieval: the model gets a search_manuals tool and decides what to look up and when, loading data at runtime. It can search again with better words when the first result misses, but it is slower and needs a well-described tool.

The article notes that a hybrid can suit less dynamic domains, and that Claude Code itself loads some files up front and retrieves the rest just in time. For your assistant, a sensible starting point is the one you already sketched: a search_manuals tool the model calls, returning a few short chunks with their page numbers.

A common mix-up

"The window is huge, so retrieval is unnecessary." The window can hold 240,000 tokens, but that does not make it a good idea. You would pay for all of it at every call, and accuracy and recall can degrade as it fills. Retrieval keeps the window small and also lets you show the student which page the answer came from.

Check yourself

A student types: "why does my cut keep burning at the edges?" The manual section is titled "Reducing char: speed and air-assist settings". Which search is more likely to find that section?

Show the answer

Embedding search. The two texts share little vocabulary but describe the same problem, which is what embeddings are built to capture.

Worked example and practice 8 min

Now put the three places together. The skill is sorting each fact the assistant needs into one of three homes: window (this request only), notes (saved, small, specific, needed on later visits), or library (large reference material, searched on demand).

Worked example

Sort these four facts for the makerspace assistant: (a) "Never book a machine for a student who is not trained on it." (b) "Sam is trained on the 3D printer but not the laser cutter." (c) The 40-page laser cutter manual. (d) The calendar result for tomorrow, just fetched.

  1. (a) is a rule that applies to every request. It is short and always needed, so it goes in the system prompt, which is part of the window on every call.
  2. (b) is a small fact about one student, needed on later visits. It must survive the end of a session, so it is a note. The program loads Sam's note at session start, or the model calls a notes tool.
  3. (c) is large reference material. Only a page or two is relevant to any question, so it lives in the library, and a search tool brings back the chunks needed.
  4. (d) is a fresh result for this question only. It is useful now and stale tomorrow, since bookings change, so it lives only in the window for this session. It is never saved as a fact, and it can be cleared once used.
Your turn

Sort these four facts the same way, and give a one-line reason for each. Step 1 is done for you: "(e) The assistant's tone: friendly, brief, no jargon" is in the system prompt, because it applies to every reply and is short.

(f) "Priya asked to be reminded that her laser cutter slot needs a safety buddy." (g) The 25-page 3D-printer troubleshooting guide. (h) The model's own request to check_calendar from three steps ago, with its already-used result.

Show a solution

(f) is a note: a small fact about one student, wanted on a later visit. (g) is library: large reference text, searched by chunk, never pasted whole. (h) is window only, and a good candidate to clear: the model has already used it, and it would otherwise be paid for again at every later step.

If you put (g) in the system prompt, you would pay for 25 pages at every call. If you stored (h) as a note, you would save stale data that could mislead the assistant next week.

Stretch: a budget thought

Your sponsor's budget is tight. Using Figure 1's idea, name two things from this lesson you would do first to cut cost per request, and one thing you would test before trusting them.

Show a sample answer

First, retrieve a few short chunks instead of whole pages, since tool results dominate the window. Second, clear tool results once used, and keep the system prompt and tool descriptions tight, since they are re-sent at every call. Test: run twenty real student questions and check that answers stay correct after the trimming, because a leaner window only helps if the answers stay right.

Summary 3 min

  • The context window is everything the model sees for one call: system prompt, tool descriptions, messages, tool results and its own output. The model keeps nothing between calls; your program re-sends the history.
  • Within a run, tool results pile up and are paid for again at every step, and a fuller window can be a less accurate one (context rot). Clear or compact what you no longer need.
  • Between sessions the window is empty. Anything the assistant should know later must be saved as notes, as small specific facts, and loaded back.
  • Retrieval finds the right chunk of a long manual so only that chunk enters the window. Up front or just in time are both valid; the choice is a design trade-off.
