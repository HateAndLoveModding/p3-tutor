The program around the model, not the model, runs the tool. It then puts the result back in front of the model and calls the model again. Today's question is sharper: when the program calls the model again, what exactly does it hand over? That is the context.

The context window 5 min

Start with a concrete case. A student types: "Is the laser cutter free Friday afternoon, and what material can't I put in it?" Your program calls the model. What does the model receive?

Not the student's question alone. It receives one long block of text made of several parts:

  • the system prompt: your standing instructions ("You are the makerspace assistant. Never book without confirming.");
  • the tool descriptions: the name and explanation of each tool;
  • the conversation so far, including the student's message;
  • every tool call made and every result returned in this request.

All of that text, together with the reply the model is about to write, must fit inside the context window: the maximum amount of text, counted in tokens, that the model can handle in one call. A token is a chunk of text, often a short word or part of a longer one. The model only knows what is in this block. Anything not in it does not exist for the model at that step.

The word "context" is used for two things, so keep them apart: the window is the limit, and the context is what you actually put in it this call.

Window sizes differ between models and change often, so look up the figure for the model you choose rather than memorising one. For the design review, the size matters less than the next idea: filling the window has a cost.

Why the window is a budget, not just a limit

Two costs follow, and your sponsor cares about both.

Money. Model usage is typically priced by tokens read and written, so a bigger context on each call costs more on each call. Details vary by provider; the pattern does not.

Quality. Anthropic's engineering team describes context as "a finite resource with diminishing marginal returns": as the window fills, the model's ability to recall details from it tends to get worse, an effect often called context rot. Their goal is the smallest set of high-signal tokens that gets the job done. More is not better; relevant is better.

A common mix-up

"A bigger context window means the model remembers more, so memory is solved." It is tempting because the window is the only thing that looks like memory. But the window is emptied at the end of every call and rebuilt by your program. A bigger window lets you hold more during one task. It does nothing for what the assistant knows tomorrow, and it makes each call more expensive and, past a point, less accurate.

What is kept between steps 6 min

Inside one request, the agent loop makes several model calls (that was learning record 0002's point: every step is a separate call). So how does step 3 know what happened in step 1? Because your program keeps a list and sends all of it again.

Here is the list for "Is the laser cutter free Friday at 3 pm, and what can't I cut?" Each row is one model call, and each call receives everything above it:

This list is the agent's working memory, or short-term memory: everything kept between steps of a single request. It is just text appended to a Python list. Roughly:

messages = [system_prompt_and_tools, student_question]
while True:
    reply = call_model(messages)      # sends the WHOLE list
    messages.append(reply)
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_request)
    messages.append(result)           # now step 2 can see it

Tool results are the usual space hog. A manual search might return three long pages of text, and those pages are then re-sent on every later call in the request, even if only one sentence mattered.

Worked example: counting what you pay for

Suppose the setup (system prompt plus tool descriptions) is 1,000 tokens, the question is 50, and each tool call plus its result adds 2,000. How many tokens does the model read across the three calls of a two-tool request?

  1. Call 1 reads setup + question: 1,000 + 50 = 1,050.
  2. Call 2 also reads the first tool call and result: 1,050 + 2,000 = 3,050.
  3. Call 3 also reads the second pair: 3,050 + 2,000 = 5,050.
  4. Total read: 1,050 + 3,050 + 5,050 = 9,150 tokens, although the "new" information was only 4,050 tokens. The rest is re-reading.

The takeaway for your budget: cost grows faster than the number of steps, so a tool that returns less text saves money on every later call. (These token numbers are made up for arithmetic; measure your own.)

When the window fills up 4 min

A long task can fill the window, and quality drops before it is literally full. Anthropic's engineering team describes three tools for long tasks, all from the same article:

  • Compaction: when the conversation nears the limit, have the model summarise it, keep the decisions and open problems, drop the repetitive detail, and start a fresh window with that summary.
  • Clearing old tool results: a light-touch version. Once a search result has been used, delete the raw text from the list.
  • Sub-agents: a helper does a messy job in its own clean window and returns only a short summary, often a thousand or two tokens, to the main agent. (Whether that pays off is a later lesson.)

Notice the trade. Every one of these throws information away. Compaction can drop a detail that turns out to matter, so the usual advice is to keep what is likely to be needed and test that nothing important is lost.

For the makerspace assistant, most requests are short: a question, one or two tool calls, an answer. Compaction is a problem for long sessions, not for the typical one. Clearing bulky tool results is the cheap habit worth building in from the start.

What is kept between sessions 6 min

A session is one conversation or one request from start to finish. When it ends, your program throws the list away, and the model never held it anyway. So by default, nothing is kept between sessions. Tomorrow the same student starts with an assistant that has never met them.

Anything the assistant should remember has to be written to storage by the program and loaded into a later context on purpose. That stored information is long-term memory. It can be a file, a database row, anything your Python can save and read. The model's role is only to decide what is worth saving and to read what you load.

Notes as memory

The simplest pattern is notes. Anthropic's article calls it structured note-taking: the agent writes notes to storage outside the context window and reads them back later. Their examples are keeping a to-do list or maintaining a NOTES.md file, which track progress and dependencies across many tool calls. (You are looking at the same idea in this workspace: NOTES.md is how your tutor remembers you between sessions.)

For the assistant, a notes entry for a student might look like this:

{
  "student_id": "s-4417",
  "trained_on": ["laser_cutter", "3d_printer"],
  "training_date": {"laser_cutter": "2026-09-14"},
  "preferences": "usually books Friday afternoons"
}

Two tools handle it: read_student_record(student_id) and update_student_record(student_id, changes). The model asks for the record; the program loads it into the context for that session. It does not need to be a clever "memory system", just a record the program can find.

A common mix-up

"Save everything the student says, then load it all next time." It feels safe, but it refills the window with old chat, costs tokens on every call, and invites stale facts. A saved "the laser cutter is booked Friday" is wrong next week. Save durable facts (training status, preferences); fetch changing facts (the calendar) fresh. This also connects to something you noticed with your homework chatbot: confident, outdated facts. Saved copies of changing facts are one way an assistant ends up doing the same.

Retrieval: finding the right page 5 min

Now the manuals. Say the laser cutter manual is 120 pages. Putting it all in the context on every call would be slow, costly and noisy. Instead the program keeps the manual in a store and fetches only the few passages that matter for the current question. That is retrieval: searching outside the window and loading only the best matches into it. Putting retrieved text into the model's input to answer from is often called retrieval-augmented generation, or RAG.

One check first. Anthropic notes that if a knowledge base is smaller than about 200,000 tokens (roughly 500 pages), you can simply include the whole thing in the prompt and skip retrieval, with prompt caching making that faster and cheaper. Whether your manuals fit is a number you can count, and it is a fair design-review question: do we need retrieval at all?

How retrieval works

  1. Chunk. Split each manual into chunks: small passages, usually no more than a few hundred tokens.
  2. Index. Make each chunk searchable, in one or both of two ways.
  3. Search. For a question, find the best-matching chunks and return the top few.
  4. Load. Put those chunks in the context, as a tool result, and let the model answer from them.

The two ways to index, per Anthropic's explanation:

  • Embeddings turn each chunk into a list of numbers that encodes its meaning, so a search finds chunks that mean something similar to the question even with different words. A question like "how do I stop the blade from burning the wood" can match a passage titled "Reducing char on cuts".
  • BM25 is plain keyword matching that ranks chunks by exact words. It is strong on unique terms such as error codes: Anthropic's example is the query "Error code TS-999", where meaning-based search may return general error-code pages while BM25 finds the exact string.

Anthropic recommends combining both. For manuals full of model numbers, settings names and error codes, that advice applies directly to you.

Retrieval is a tool, so it fits the loop you know

In your assistant, retrieval is just another tool: search_manuals(machine, query). The model decides when to call it, and the result lands in the context like any tool result. Anthropic calls fetching data at the moment it is needed "just-in-time" retrieval, versus loading data up front before the model runs. Their own coding tool does both: it loads a project instructions file up front and fetches other files on demand. A sensible makerspace mix is the same: load the student's short record up front, search the manuals on demand.

Retrieval is not perfect. Anthropic measured how often the right chunk was missing from the top 20 results: 5.7% for a baseline, falling to 1.9% with their full improved pipeline (those figures are averages from their tests, not a promise for your manuals). Even good retrieval sometimes misses, so the assistant should say when it found nothing relevant rather than guess.

A common mix-up

"Retrieval means the model has learned the manuals." The model learns nothing. Retrieval is search plus pasting: the chosen chunks sit in this call's context and vanish with it. Update a manual and the next search finds the new text, with no retraining. That is why retrieval, not training, is the right tool for manuals that change.

Worked example and practice 5 min

Worked example: sorting one request

Request: a returning student asks, "Can I use the vinyl cutter on Thursday, and how do I change the blade?" Decide where each piece of information lives and what the program does.

  1. Always needed: rules and tool descriptions. These go in the system prompt, in the context on every call.
  2. Remembered from before: is this student trained on the vinyl cutter? Durable and small, so it is a saved record. The model calls read_student_record; the result enters the context.
  3. Changing: Thursday's availability. Never saved; the model calls check_calendar("vinyl cutter", Thursday).
  4. Large: the blade procedure. It lives in the manual store; the model calls search_manuals("vinyl cutter", "change blade") and only the best chunks enter the context.
  5. After the answer: clear the bulky manual excerpt if the chat continues. If a new durable fact appeared (for example, the student mentions finishing a new course), call the update tool to save it.

Summary 2 min

  • The model sees only the context window: system prompt, tool descriptions, history, tool results. It is rebuilt and re-paid for on every call.
  • Between steps, your program keeps a list and re-sends it whole, so cost grows with each step; trim bulky tool results, and compact only when long tasks need it.
  • Between sessions, nothing persists unless your program saves it. Save small, durable facts as notes or records; fetch changing facts fresh.
  • For large documents, use retrieval: chunk, search by meaning and keywords, load only the best chunks, and check first whether the whole thing fits in the window.
